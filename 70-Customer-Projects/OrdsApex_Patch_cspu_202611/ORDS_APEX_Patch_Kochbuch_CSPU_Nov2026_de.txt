==========================================================================
  ORDS-Update + APEX-Patch - CSPU November 2026
  ORDS 26.x  -> 26.3.1.303.1615   (ords-latest.zip, Stand 2026-11-26)
  APEX 26.2  -> 26.2.1            (Patch Set Bundle 40040466)
==========================================================================

  Zielgruppe : Administrator des Application Servers (oracle + root/sudo)
  Umgebung   : ORDS standalone (Jetty) als systemd-Service auf dem
               Application Server, Apache/Nginx davor, APEX in einer PDB.
               Alles wird VOM APPLICATION SERVER aus gemacht (SQL*Plus
               dort, keine Anmeldung am DB-Server noetig).
  Erstellt   : 2026-11-26
  Grundlage  : - README.txt im Patch 40040466 (APEX 26.2.1, Okt 26 2026),
                 Abschnitt "(III) Patch Installation Instructions"
               - Oracle CPU431 (CSPU Nov 2026, Database Products):
                 ORDS 24.2.0-26.3.0 betroffen (bis CVSS 9.8) -> ORDS 26.3.1,
                 APEX 26.2.0 betroffen (CVE-2026-114849/-114850) -> 26.2.1
               - IHateWeblogic/12-APEX-Ords/README.md Abschnitt 6 (Upgrade)
               - IHateWeblogic/80-FMW-Architecture/ords_architecture.md
               - Testlauf auf dem Testhost 2026-11-18 (ORDS 26.3.0 ->
                 26.3.1 in 7 s, catpatch 24 s)
  Wichtig    : - ORDS hat KEINE Patches: ein ORDS-Update ist immer eine neue
                 Software neben der alten + Upgrade des Schemas ORDS_METADATA.
               - ORDS-Schema-Upgrade und APEX-Patch sind EINWEG-Schritte in
                 der Datenbank. Der Weg zurueck ist nur ein DB-Backup.
                 -> VOR dem Termin: Restore Point / RMAN-Backup der PDB durch
                    den DBA, VM-Snapshot des Application Servers.
               - Reihenfolge: erst ORDS, dann APEX (ORDS muss >= APEX sein).

VORAUSSETZUNGEN
---------------

  - DB-Backup / Restore Point der PDB (DBA), VM-Snapshot.
  - SYS-Passwort der Datenbank (wird nur versteckt abgefragt).
  - SQL*Plus auf dem Application Server (FMW-Home ueber setfmw oder
    Instant Client) - wird in SCHRITT 0 geprueft.
  - root bzw. sudo fuer systemctl und die Unit-Datei.
  - Platz: ca. 1,5 GB unter $WORK (ZIPs 0,3 GB, Sicherung Images ca.

  - Wartungsfenster ca. 30 Minuten, APEX ist zweimal kurz weg
    (SCHRITT 5-7 und SCHRITT 8-10).

  ---------------------------------------------------
  1.1 Laufender ORDS-Prozess
  ---------------------------------------------------

  ORDS_PID=$(pgrep -u oracle -f "java.*ords.war.*serve")

  echo "ORDS_PID=$ORDS_PID"
  # Erwartet: EINE Nummer. Leer -> ORDS laeuft nicht, erst klaeren.
  # Zwei Nummern -> mehrere ORDS-Instanzen, nur eine pro Durchlauf!

  tr '\0' ' ' < /proc/$ORDS_PID/cmdline | tee $LOGDIR/01_ords_prozess.txt
  # Erwartet z.B.: /usr/lib/jvm/jre-21-openjdk/bin/java
  #   -Doracle.dbtools.cmdline.home=/oracle/product/ords/ords ...
  #   -jar /oracle/product/ords/ords/ords.war --config /oracle/product/ords/config serve
  # Pruefen: steht hinter --config derselbe Pfad wie $ORDS_CONFIG?

  ---------------------------------------------------
  1.2 Alte ORDS-Software und Java aus dem Prozess ableiten
  ---------------------------------------------------

  OLD_WAR=$(tr '\0' '\n' < /proc/$ORDS_PID/cmdline | grep "ords.war$")

  OLD_HOME=$(dirname "$OLD_WAR")

  ORDS_JAVA=$(readlink -f /proc/$ORDS_PID/exe)

  echo "OLD_HOME=$OLD_HOME  ORDS_JAVA=$ORDS_JAVA"
  # Erwartet z.B.: OLD_HOME=/oracle/product/ords/ords
  #                ORDS_JAVA=/usr/lib/jvm/java-21-openjdk-.../bin/java
  # OLD_HOME leer -> der Prozess startet ords ohne "-jar ...ords.war":
  # Pfad aus der Ausgabe von 1.1 (cmdline.home=...) von Hand setzen.

  "$ORDS_JAVA" -version
  # Erwartet: 17 oder 21 (ORDS 26.x braucht Java 17 oder 21).

  echo "export OLD_HOME=$OLD_HOME" >> $WORK/ords_apex_env.sh

  echo "export ORDS_BASE=$(dirname $OLD_HOME)" >> $WORK/ords_apex_env.sh

  echo "export JAVA_HOME=${ORDS_JAVA%/bin/java}" >> $WORK/ords_apex_env.sh

  . $WORK/ords_apex_env.sh

  echo "ORDS_BASE=$ORDS_BASE JAVA_HOME=$JAVA_HOME"
  # Erwartet: /oracle/product/ords  und das Java-Verzeichnis ohne /bin/java

  ---------------------------------------------------
  1.3 Welcher systemd-Service startet ORDS?
  ---------------------------------------------------

  systemctl status $ORDS_PID | head -3

  #   * ords.service - Oracle REST Data Services
  #     Loaded: loaded (/etc/systemd/system/ords.service; enabled; ...)
  # Der Name vor ".service" ist ORDS_UNIT, der Pfad hinter "loaded (" ist
  # die Unit-Datei.

  echo "export ORDS_UNIT=ords" >> $WORK/ords_apex_env.sh
  # "ords" durch den Namen aus der Ausgabe darueber ersetzen, wenn er
  # anders heisst (z.B. ords@ords_1).

  . $WORK/ords_apex_env.sh

  # kein Treffer, ExecStart ruft ords.sh -> Pfad steht in /etc/ords.conf

  # Nur bei Fall B noetig. "No such file" bei Fall A ist normal.

==========================================================================
BEKANNTE PROBLEME
==========================================================================

  Problem : "ords: command not found" / "Unable to locate a Java Runtime"
  Ursache : JAVA_HOME fehlt im Terminal.
  Loesung : SCHRITT 0.3 (Variablen laden) - JAVA_HOME steht seit 1.2 in
            ords_apex_env.sh.

  Problem : SCHRITT 6 fragt nach Tablespace, Proxy-User oder Features.
  Ursache : ORDS findet keine bestehende Installation (falsche Config oder
            falscher Pool).
  Loesung : Strg+C, NICHTS installieren. --config und Pool pruefen (1.5).

  Problem : ORA-01017 in SCHRITT 6 oder 9.
  Ursache : falsches SYS-Passwort, oder SYS darf sich remote nicht
            anmelden (Passwortdatei / REMOTE_LOGIN_PASSWORDFILE).
  Loesung : Mit dem DBA klaeren; Test: sqlplus sys@$DB_CONNECT as sysdba

  Problem : show con_name zeigt CDB$ROOT.
  Ursache : DB_CONNECT zeigt auf den CDB-Service.
  Loesung : Service der PDB nehmen (derselbe wie im ORDS-Pool, 1.5).

  Problem : Apache/Nginx meldet 502/503 nach dem Start.
  Ursache : ORDS braucht beim ersten Start bis 60 s.
  Loesung : warten; sonst  journalctl -u $ORDS_UNIT -n 50

  Problem : APEX zeigt alte Version oder kaputte Icons.
  Ursache : Browser-Cache, oder Images nicht im /i/-Verzeichnis des
            Webservers.
  Loesung : Strg+F5; SCHRITT 8.2 / 8.4 pruefen (apex_version.js = 26.2.1
            ueber https://<server>/i/apex_version.js).

  Problem : apex_version.txt zeigt nach dem Patch weiter "26.2".
  Ursache : Der Patch schreibt diese Datei nicht neu.
  Loesung : Kein Fehler - Nachweis ist apex_version.js und dba_registry.

  Problem : ORDS lauscht auf 0.0.0.0 (alle Netzwerkkarten).
  Ursache : "--ip-addresses 0.0.0.0" in der Unit bzw. Standard von Jetty.
  Loesung : Nicht Teil dieses Termins. Spaeter: ORDS nur auf 127.0.0.1
            (standalone.binds), Zugriff nur ueber den Webserver - siehe
            IHateWeblogic/80-FMW-Architecture/ords_architecture.md.
