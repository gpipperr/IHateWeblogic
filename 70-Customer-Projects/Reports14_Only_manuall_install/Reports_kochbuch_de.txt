================================================================================
  Oracle Reports 14.1.2 installieren und konfigurieren (ohne Forms)
  (Manuelle Schritt-fuer-Schritt-Anleitung, ohne IHateWeblogic-Skripte)
================================================================================
  Zielgruppe : DBA / Systemadministrator ohne IHateWeblogic-Skripte
  Umgebung   : Oracle Linux 9, FMW 14.1.2.0.0, WebLogic 14.1.2, nur Reports
  Erstellt   : 2026-10
  Grundlage  : IHateWeblogic/09-Install/06-13 (Gunther Pipperr)
  Voraussetzung: OS_Kochbuch_de.txt + FMW_Kochbuch_de.txt vollstaendig
                 durchgefuehrt (WebLogic/FMW-Infrastruktur installiert,
                 gepatcht, Nginx mit SSL laeuft)

  WICHTIG: Dieses Kochbuch behandelt AUSSCHLIESSLICH Oracle Reports.
  Alle Forms-spezifischen Schritte (forms_template.jar, WLS_FORMS,
  Forms-Patch 39842516, Forms-Detaileinstellungen) sind bewusst
  WEGGELASSEN. Die externe Datenbank wird in keinem Schritt angelegt -
  es werden nur Schemas in einer bereits bestehenden Datenbank
  registriert.
================================================================================

VORAUSSETZUNGEN
----------------
    export ORACLE_BASE=/u01/oracle
    export ORACLE_HOME=/u01/oracle/fmw

    export DOMAIN_HOME=/u01/user_projects/domains/reportRpgpi

    export WLS_MANAGED_SERVER=reportRpgpi

================================================================================
SCHRITT 1: Forms & Reports Software installieren  (als oracle)
================================================================================

  # Hinweis: Der 14.1.2-Installer liefert IMMER Forms- und
  # Reports-Binaries gemeinsam aus - einen "Reports-only"-Installertyp
  # gibt es auf Binaer-Ebene nicht. Die Beschraenkung auf Reports erfolgt
  # erst spaeter bei der Domain-Erstellung (Schritt 3) ueber die
  # tatsaechlich verwendeten Konfigurations-Templates.

  # Beide folgenden Optionen fuehren zum IDENTISCHEN Ergebnis - Option A
  # (Silent) ist die uebliche Wahl auf einem Server ohne dauerhafte
  # grafische Oberflaeche, Option B (Grafisch) fuer alle, die dem
  # Installationsassistenten lieber beim Arbeiten zusehen/Werte interaktiv
  # pruefen wollen. Nur EINE der beiden Optionen ausfuehren.

  --- Option A: Silent (Antwortdatei, empfohlen fuer Server ohne GUI) --------

  cat > $PATCH_STORAGE/fr/fr_install.rsp << 'EOF'
[ENGINE]
Response File Version=1.0.0.0.0
[GENERIC]
DECLINE_AUTO_UPDATES=true
MOS_USERNAME=
MOS_PASSWORD=
SOFTWARE_UPDATES_PROXY_SERVER=
SOFTWARE_UPDATES_PROXY_PORT=
SOFTWARE_UPDATES_PROXY_USER=
SOFTWARE_UPDATES_PROXY_PASSWORD=
ORACLE_HOME=/u01/oracle/fmw
FEDERATED_ORACLE_HOMES=
INSTALL_TYPE=Forms and Reports Deployment
JDK_HOME=/u01/oracle/java/jdk-21
EOF

  export CV_ASSUME_DISTID=OEL8

  # Natives .bin-Installerformat (NICHT "java -jar" wie bei der
  # FMW-Infrastruktur) - -ignoreSysPrereqs ist hier Standard laut
  # Oracle-Dokumentation fuer diesen Installer.
  $PATCH_STORAGE/fr/fmw_14.1.2.0.0_fr_linux64.bin \
      -silent \
      -responseFile $PATCH_STORAGE/fr/fr_install.rsp \
      -invPtrLoc /etc/oraInst.loc \
      -ignoreSysPrereqs \
      -jreLoc $JDK_HOME

  unset CV_ASSUME_DISTID
  rm -f $PATCH_STORAGE/fr/fr_install.rsp

  --- Option B: Grafisch (Installationsassistent, OUI-GUI) -------------------

  # Voraussetzung: grafische Oberflaeche erreichbar - siehe
  # FMW_Kochbuch_de.txt Schritt 1 Option B (X11-Weiterleitung per
  # "ssh -X" oder VNC, $DISPLAY gesetzt, ggf. xorg-x11-xauth installiert).

  export CV_ASSUME_DISTID=OEL8

  # Gleicher Installer-Aufruf wie Option A, aber OHNE -silent/-responseFile -
  # startet stattdessen den grafischen Oracle Universal Installer (OUI).
  # -ignoreSysPrereqs bleibt noetig, unabhaengig vom Silent-/GUI-Modus:
  $PATCH_STORAGE/fr/fmw_14.1.2.0.0_fr_linux64.bin \
      -invPtrLoc /etc/oraInst.loc \
      -ignoreSysPrereqs \
      -jreLoc $JDK_HOME

  unset CV_ASSUME_DISTID

  # Im Assistenten dieselben Werte eintragen, die in Option A in der
  # Response-Datei standen:
  #   Oracle Home:        /u01/oracle/fmw  (bereits durch die
  #                        FMW-Infrastruktur belegt, siehe FMW_Kochbuch_de.txt)
  #   Installationstyp:   "Forms and Reports Deployment"
  #                        (NICHT "Standalone Forms Builder" - das ist nur
  #                        fuer eine Forms-Entwickler-Arbeitsstation gedacht)
  #   MOS-Zugangsdaten:   leer lassen / Schritt ueberspringen
  #   Proxy-Einstellungen: leer lassen, falls kein Proxy benoetigt wird
  #
  # Der Assistent fuehrt am Ende dieselbe Pruefung/Installation aus wie
  # Option A - Dauer und Ergebnis sind identisch.

  # Dauer (beide Optionen): ca. 10-20 Minuten. Installationslog:
  # /u01/app/oraInventory/logs/

  # Kontrolle (beide Optionen, NUR Reports relevant)
  $ORACLE_HOME/OPatch/opatch version
  ls $ORACLE_HOME/reports/
  # Die Reports-Werkzeuge liegen direkt unter $ORACLE_HOME/bin (NICHT unter
  # $ORACLE_HOME/reports/bin):
  test -x $ORACLE_HOME/bin/rwrun && echo "rwrun vorhanden - OK"
  test -x $ORACLE_HOME/bin/rwconverter && echo "rwconverter vorhanden - OK"


================================================================================
SCHRITT 2: Reports-Patch einspielen  (als oracle)
================================================================================

  # WICHTIG: Von den beiden aktuellen Forms&Reports-QPR-Patches wird HIER
  # NUR der Reports-Patch eingespielt. Der zweite (Forms-QPR) wird
  # bewusst WEGGELASSEN, da reines Forms-Patch ohne Reports-Bezug.
  #   Reports-Patch (einspielen):      39600348  (Stand Aug 2026)
  #   Forms-Patch (NICHT einspielen):  39842516  (Stand Sep 2026)
  # Aktuelle Patchnummern per MOS KA204 ermitteln (aendern sich jedes
  # Quartal) - siehe IHateWeblogic/09-Install/docs/00-patch-references.md
  # und oracle_software_version.conf fuer den jeweils aktuellen Stand.

  # Falls ein aelterer Reports-QPR bereits installiert ist (z.B. 38827528
  # aus Januar 2026), wird er vom neuen Patch ersetzt - vorher zurueckrollen:
  $ORACLE_HOME/OPatch/opatch lspatches | grep 38827528
  # falls gefunden:
  $ORACLE_HOME/OPatch/opatch rollback -id 38827528

  # Patch-ZIP zuerst entpacken - opatch arbeitet im entpackten Verzeichnis
  unzip -q $PATCH_STORAGE/patches/39600348/p39600348_*.zip -d /tmp/mw_patches
  cd /tmp/mw_patches/39600348
  $ORACLE_HOME/OPatch/opatch prereq CheckConflictAgainstOHWithDetail -ph .
  # Pruefen: "Prereq ... passed". Steht dort "failed", NICHT weitermachen -
  # opatch meldet am Ende trotzdem "OPatch succeeded".
  $ORACLE_HOME/OPatch/opatch apply -silent -jdk $JDK_HOME
  cd -
  $ORACLE_HOME/OPatch/opatch lspatches | grep 39600348

  # FMW PERL Security Patch 38590500 - gehoert HIERHER, nicht ins
  # FMW-Kochbuch: seine Komponente (oracle.perlint) bringt erst die
  # Reports-Installation mit. In der reinen WebLogic-Infrastruktur wuerde
  # opatch ihn mit "none of the components from patch are present"
  # ueberspringen (Ende: "completed with warnings", aber NICHT installiert).
  unzip -q $PATCH_STORAGE/patches/38590500/p38590500_*.zip -d /tmp/mw_patches
  cd /tmp/mw_patches/38590500
  $ORACLE_HOME/OPatch/opatch prereq CheckConflictAgainstOHWithDetail -ph .
  $ORACLE_HOME/OPatch/opatch apply -silent -jdk $JDK_HOME
  cd -
  $ORACLE_HOME/OPatch/opatch lspatches | grep 38590500
  # Erwartet: eine Zeile mit 38590500. Fehlt sie und stand in der Ausgabe
  # "none of the components from patch are present", ist Perl in diesem Home
  # nicht installiert - dann ist der Patch hier nicht anwendbar.
  rm -rf /tmp/mw_patches

  # /etc/oraInst.loc wird automatisch gefunden, kein -invPtrLoc noetig.

  # BEKANNT UND UNKRITISCH bei 39600348 (bestaetigt 2026-10-14): Die Ausgabe
  # endet haeufig mit "OPatch Session completed with warnings" statt "OPatch
  # succeeded" - das ist KEIN Fehlschlag, solange vorher
  # "Patch 39600348 successfully applied." steht. Grund sind zwei
  # Linker-Warnungen aus dem internen Relink-Schritt (make/ld), die Oracle
  # selbst in diesem QPR mit ausliefert:
  #   1. "the use of `mktemp' is dangerous, better use `mkstemp'" - reine
  #      glibc-Hinweismeldung, weil Oracle-Code (sobwv.c) noch das veraltete
  #      mktemp() nutzt. Kein Fehler, nicht von uns behebbar.
  #   2. "size of symbol `zrmpu_functypes' changed from 16 ... to 64 ..." -
  #      der Linker meldet nur, dass ein Symbol in der neu gepatchten
  #      librw.a groesser ist als ein "common"-Platzhalter in rwsjni.o
  #      (Reports-JNI-Bridge). Waere das ein echter Konflikt, gaebe es einen
  #      harten "multiple definition"-Fehler statt einer Warnung.
  # Trotzdem danach kurz gezielt testen, da genau rwsjni betroffen ist:
  # einen Report ueber rwservlet laufen lassen (PDF und HTML), rwrun von der
  # Kommandozeile, rwconverter, showjobs.


================================================================================
SCHRITT 3: RCU-Schema in der bestehenden Datenbank registrieren  (als oracle)
================================================================================

  # WICHTIG: Dieser Schritt legt KEINE Datenbank an und erzeugt KEINE
  # Instanz - die Datenbank existiert bereits extern und wird von einem
  # anderen Team betrieben. RCU registriert hier ausschliesslich Schemas
  # (Tabellen/Benutzer) INNERHALB dieser bestehenden Datenbank.

  # Erreichbarkeit vorab pruefen
  nc -zv "$DB_HOST" "$DB_PORT"

  # Optional: Falls ein eigener Tablespace gewuenscht ist (sonst legt RCU
  # automatisch eigene Tablespaces an) - dieser SQL-Befehl muss vom
  # Datenbank-Team der EXTERNEN Datenbank ausgefuehrt werden, nicht von
  # uns:
  #   CREATE TABLESPACE FMW_DATA
  #     DATAFILE '/u01/oradata/mydb/fmw_data01.dbf'
  #     SIZE 500M AUTOEXTEND ON NEXT 100M MAXSIZE UNLIMITED;

  # Beide folgenden Optionen fuehren zum IDENTISCHEN Ergebnis (dieselben 9
  # Schemas werden angelegt) - Option A (Silent) ist die uebliche Wahl auf
  # einem Server ohne dauerhafte grafische Oberflaeche, Option B (Grafisch)
  # fuer alle, die dem RCU-Assistenten lieber beim Arbeiten zusehen/Werte
  # interaktiv pruefen wollen. Nur EINE der beiden Optionen ausfuehren.

  --- Option A: Silent (Kennwortdatei, empfohlen fuer Server ohne GUI) -------

  # RCU-Kennwortdatei anlegen (SYS-Kennwort + je ein Kennwort pro Schema).
  # WICHTIG: Datei nur temporaer, danach sofort loeschen (enthaelt
  # Klartext-Kennwoerter).
  umask 077
  cat > /tmp/rcu_passwords.txt << 'EOF'
<SYS_PASSWORD>
<SCHEMA_PASSWORD>
<SCHEMA_PASSWORD>
<SCHEMA_PASSWORD>
<SCHEMA_PASSWORD>
<SCHEMA_PASSWORD>
<SCHEMA_PASSWORD>
<SCHEMA_PASSWORD>
<SCHEMA_PASSWORD>
<SCHEMA_PASSWORD>
EOF
  chmod 600 /tmp/rcu_passwords.txt

  # Vorab-Test: SYSDBA-Anmeldung pruefen, bestehenden Schema-Prefix
  # ausschliessen (Namenskonflikt vermeiden)
  $ORACLE_HOME/oracle_common/bin/rcu -silent -listSchemas \
      -connectString "${DB_HOST}:${DB_PORT}/${DB_SERVICE}" \
      -dbUser sys -dbRole sysdba < /tmp/rcu_passwords.txt

  # RCU-Schemas anlegen. 8 Komponenten ergeben 9 Schemas (WLS hat ein
  # Unterschema WLS_RUNTIME zusaetzlich).
  #
  # WICHTIG - Connect-String-Falle: IMMER "host:port/service_name" mit
  # SCHRAEGSTRICH verwenden (adressiert einen PDB-Service). Ein
  # Doppelpunkt ("host:port:SID") wuerde stattdessen die CDB ansprechen -
  # das ist bei Multitenant-Datenbanken (Standard seit Oracle 12c) fast
  # immer falsch.
  $ORACLE_HOME/oracle_common/bin/rcu \
      -silent \
      -createRepository \
      -connectString "${DB_HOST}:${DB_PORT}/${DB_SERVICE}" \
      -dbUser sys \
      -dbRole sysdba \
      -schemaPrefix "${DB_SCHEMA_PREFIX}" \
      -component STB -component MDS -component OPSS -component IAU \
      -component IAU_APPEND -component IAU_VIEWER -component UCSUMS -component WLS \
      -f < /tmp/rcu_passwords.txt

  # Kennwortdatei sofort entfernen
  shred -u /tmp/rcu_passwords.txt 2>/dev/null || rm -f /tmp/rcu_passwords.txt

  --- Option B: Grafisch (RCU-Assistent) --------------------------------------

  # Voraussetzung: grafische Oberflaeche erreichbar - siehe
  # FMW_Kochbuch_de.txt Schritt 1 Option B (X11-Weiterleitung per
  # "ssh -X" oder VNC, $DISPLAY gesetzt, ggf. xorg-x11-xauth installiert).

  # Gleiches Werkzeug wie Option A, aber OHNE -silent/-connectString/
  # -component-Parameter - startet stattdessen den grafischen RCU-Assistenten:
  $ORACLE_HOME/oracle_common/bin/rcu

  # Im Assistenten dieselben Werte eintragen, die in Option A als
  # Kommandozeilenparameter standen:
  #
  #   Bildschirm "Create Repository":
  #     Create Repository  ->  System Load and Product Load
  #
  #   Bildschirm "Database Connection Details":
  #     Database Type:  Oracle Database
  #     Host Name:      ${DB_HOST}
  #     Port:           ${DB_PORT}
  #     Service Name:   ${DB_SERVICE}   <- WICHTIG: das Feld "Service Name"
  #                     verwenden, NICHT "SID" (dieselbe Connect-String-Falle
  #                     wie in Option A - ein SID wuerde die CDB statt der
  #                     PDB ansprechen, bei Multitenant-Datenbanken falsch)
  #     Username:       sys
  #     Password:       <SYS_PASSWORD>
  #     Role:           SYSDBA
  #     -> Next testet die Verbindung automatisch
  #
  #   Bildschirm "Select Components":
  #     Create a new Prefix: ${DB_SCHEMA_PREFIX}
  #     Nur folgende Komponenten ankreuzen (nicht mehr, nicht weniger -
  #     identisch zu den "-component"-Parametern in Option A):
  #       STB, MDS, OPSS, IAU, IAU_APPEND, IAU_VIEWER, UCSUMS, WLS
  #
  #   Bildschirm "Schema Passwords":
  #     "Use same passwords for all schemas" ankreuzen, Passwort eingeben
  #     (oder je Schema einzeln, wie in der Kennwortdatei von Option A)
  #
  #   Bildschirm "Map Tablespaces":
  #     Vorschlag uebernehmen, ausser ein eigener Tablespace wurde vorab
  #     angelegt (siehe Hinweis oben)
  #
  #   Bildschirm "Summary"  ->  Create
  #   Bildschirm "Completion Summary"  ->  Close
  #
  # Der Assistent fuehrt am Ende dieselbe Schema-Erstellung aus wie
  # Option A - Ergebnis ist identisch (9 Schemas mit Prefix ${DB_SCHEMA_PREFIX}_).

  # RCU-Logs (beide Optionen): $ORACLE_HOME/oracle_common/rcu/log/

  # Verifikation GEGEN DIE BESTEHENDE DATENBANK (per sqlplus, falls
  # Oracle-Client lokal verfuegbar, sonst vom DB-Team ausfuehren lassen):
  #   SELECT username FROM dba_users
  #   WHERE username LIKE UPPER('${DB_SCHEMA_PREFIX}') || '_%'
  #   ORDER BY username;
  # Erwartung: 9 Zeilen (STB, MDS, OPSS, IAU, IAU_APPEND, IAU_VIEWER,
  # UCSUMS, WLS, WLS_RUNTIME), jeweils mit Prefix ${DB_SCHEMA_PREFIX}_


================================================================================
SCHRITT 4: WebLogic-Domain anlegen (nur Reports, kein Forms)  (als oracle)
================================================================================

  # Voraussetzung: grafische Oberflaeche erreichbar - siehe
  # FMW_Kochbuch_de.txt Schritt 1 Option B (X11-Weiterleitung per
  # "ssh -X" oder VNC, $DISPLAY gesetzt, ggf. xorg-x11-xauth installiert).

  # WICHTIG vor dem Start: Falls $DOMAIN_HOME/config/config.xml bereits
  # existiert, im Assistenten NICHT "Create Domain" waehlen - das wuerde
  # versuchen, am selben Pfad eine neue Domain anzulegen und schlaegt dann
  # entweder fehl oder fragt nach einem Update. Stattdessen "Update Domain"
  # verwenden oder vorher einen anderen DOMAIN_HOME waehlen.
  test -f $DOMAIN_HOME/config/config.xml && echo "ACHTUNG: Domain existiert bereits"

  # Fusion Middleware Configuration Wizard starten:
  $ORACLE_HOME/oracle_common/common/bin/config.sh

  # Im Assistenten folgende Werte eintragen/auswaehlen. Im Vergleich zu
  # einer Forms+Reports-Standardanleitung wird hier BEWUSST NICHT die
  # Vorlage "Oracle Forms" angehakt - das ist der einzige Unterschied, der
  # aus dieser Domain eine reine Reports-Domain macht.
  #
  #   Bildschirm "Welcome":
  #     Create a New Domain
  #
  #   Bildschirm "Create Domain":
  #     Domain Location: ${DOMAIN_HOME}
  #
  #   Bildschirm "Templates":
  #     "Create Domain Using Product Templates" (NICHT "...Using Custom
  #     Template")
  #     Ankreuzen:
  #       [x] Oracle JRF - 14.1.2.0.0   (zieht "Oracle Enterprise Manager"
  #                                      als Abhaengigkeit automatisch mit -
  #                                      wird fuer Schritt 8 gebraucht)
  #       [x] Oracle Reports - 14.1.2.0.0
  #     NICHT ankreuzen:
  #       [ ] Oracle Forms   <- bewusst weggelassen, reines Reports-Thema
  #
  #   Bildschirm "Application Location":
  #     Vorschlag uebernehmen (Standard-Pfad neben $DOMAIN_HOME)
  #
  #   Bildschirm "Administrator Account":
  #     Name:     weblogic
  #     Password: <WLS_ADMIN_PASSWORD>
  #     (Kennwort-Richtlinie: mindestens 8 Zeichen, mindestens eine Ziffer
  #     ODER ein Sonderzeichen - sonst Fehler 60455)
  #
  #   Bildschirm "Domain Mode and JDK":
  #     Domain Mode: Production
  #     JDK:         $JDK_HOME (falls nicht automatisch erkannt, "Browse"
  #                  verwenden)
  #
  #   Bildschirm "Database Configuration Type":
  #     RCU Data  (NICHT "Manual Configuration" - "RCU Data" liest die
  #     Schema-Infos direkt aus der in Schritt 3 angelegten STB-Tabelle in
  #     der Datenbank und befuellt danach ALLE JRF-Datenquellen automatisch -
  #     vollstaendiger als eine manuelle Einzelkonfiguration)
  #       Vendor:          Oracle
  #       Driver:          Oracle's Driver (Thin) for Service connections
  #       Service:         ${DB_SERVICE}   <- WICHTIG: Service-Feld, nicht
  #                        SID (dieselbe Connect-String-Falle wie in
  #                        Schritt 3)
  #       Host Name:       ${DB_HOST}
  #       Port:            ${DB_PORT}
  #       Schema Owner:    ${DB_SCHEMA_PREFIX}_STB
  #       Schema Password: <SCHEMA_PASSWORD>  (Kennwort des STB-Schemas aus
  #                        Schritt 3)
  #     -> "Get RCU Configuration" klicken, danach weiter
  #
  #   Bildschirm "JDBC Component Schema":
  #     Die aus "Get RCU Configuration" vorbelegten Werte pruefen, nichts
  #     aendern (alle Schemas verwenden denselben Prefix ${DB_SCHEMA_PREFIX})
  #
  #   Bildschirm "JDBC Component Schema Test":
  #     "Test All Connections" - alle Zeilen muessen auf "Success" stehen,
  #     sonst DB-Erreichbarkeit/Kennwoerter pruefen ("nc -zv $DB_HOST $DB_PORT")
  #
  #   Bildschirm "Advanced Configuration":
  #     Ankreuzen (nur diese beiden - entspricht genau dem, was eine
  #     manuelle Konfiguration hier setzen wuerde):
  #       [x] Administration Server
  #       [x] Managed Servers, Clusters and Coherence
  #
  #   Bildschirm "Administration Server":
  #     Server Name:     AdminServer
  #     Listen Address:  localhost
  #     Listen Port:     ${WLS_ADMIN_PORT}
  #
  #   Bildschirm "Managed Servers":
  #     Vorhandenen Beispiel-Eintrag anpassen bzw. einen Server hinzufuegen:
  #       Server Name:     ${WLS_MANAGED_SERVER}
  #       Listen Address:  localhost
  #       Listen Port:     ${WLS_REPORTS_PORT}
  #     KEINEN zweiten Server fuer Forms hinzufuegen - das waere der
  #     "/Servers/WLS_FORMS"-Block, den eine Forms+Reports-Standardanleitung
  #     hier haette und den dieses Kochbuch bewusst weglaesst.
  #
  #   Bildschirm "Configuration Summary" -> Create
  #   Bildschirm "Configuration Progress" -> warten bis 100%
  #   Bildschirm "Configuration Success" -> Close
  #
  # Dauer: ca. 5-10 Minuten. Fortschritt/Fehler sind im Assistenten selbst
  # ueber "View Log" einsehbar.

  # Kontrolle
  test -f $DOMAIN_HOME/config/config.xml && echo "Domain angelegt - OK"
  grep -q "${WLS_MANAGED_SERVER}" $DOMAIN_HOME/config/config.xml && echo "Managed Server vorhanden - OK"

  # Node-Manager-Konfiguration
  mkdir -p $DOMAIN_HOME/nodemanager
  cat > $DOMAIN_HOME/nodemanager/nodemanager.properties << EOF
ListenAddress=127.0.0.1
ListenPort=${WLS_NODEMANAGER_PORT}
SecureListener=false
LogLimit=0
PropertiesVersion=14.1.2
AuthenticationEnabled=true
NodeManagerHome=${DOMAIN_HOME}/nodemanager
JavaHome=${JDK_HOME}
LogFile=${DOMAIN_HOME}/nodemanager/nodemanager.log
LogLevel=INFO
EOF

  # boot.properties fuer AdminServer (automatischer Start ohne
  # interaktive Passwortabfrage - WebLogic verschluesselt die Datei beim
  # ersten Start automatisch)
  mkdir -p $DOMAIN_HOME/servers/AdminServer/security
  cat > $DOMAIN_HOME/servers/AdminServer/security/boot.properties << 'EOF'
username=weblogic
password=<WLS_ADMIN_PASSWORD>
EOF
  chmod 600 $DOMAIN_HOME/servers/AdminServer/security/boot.properties

  # Hinweis Kennwort-Richtlinie: mindestens 8 Zeichen, mindestens eine
  # Ziffer ODER ein Sonderzeichen (sonst Fehler 60455).

  # AdminServer erstmalig starten
  nohup $DOMAIN_HOME/bin/startWebLogic.sh > /tmp/adminserver_start.log 2>&1 &
  sleep 60
  curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:${WLS_ADMIN_PORT}/console/

SCHRITT 8: Reports-Benutzer und Policies anlegen  (ueber Enterprise Manager)
================================================================================

  # Berechtigungs-Kette in WebLogic/OPSS: Berechtigung (Application Policy)
  # -> Rolle (Application Role) -> Benutzer (Security Realm / myrealm).
  # Quelle: pipperr.de - Oracle Reports 14c Reports Servlet Admin Oberflaeche
  # erlauben - Monitoring und Report User anlegen; Oracle Doc ID 2072876.1
  # (REP-56071 When Attempt to Access In-Process Reports Server).
  #
  # Diese drei Benutzer/Rollen werden ueber die EM-Konsole angelegt
  # (http://<host>:9002/em), app-stripe "reports":
  #
  #   Benutzer      Rolle            Zweck
  #   weblogic      RW_ADMINISTRATOR (bereits vorhanden, nur Rolle zuweisen)
  #   monUser       RW_MONITOR       Server-Status abfragen (showjobs, getserverinfo, ...)
  #   RepRunner     RW_EXECREPORTS   Reports tatsaechlich ausfuehren
  #
  # Menuetexte unten: Englisch (Deutsch) - die deutschen Begriffe entsprechen
  # der ueblichen Oracle-EM-Uebersetzung, werden aber nur angezeigt, wenn die
  # Konsole/der Browser auf Deutsch eingestellt ist. Ohne deutsches
  # Sprachpaket/Locale erscheinen IMMER die englischen Originalbegriffe -
  # dann nach den englischen Texten navigieren.

  # 8.1 weblogic -> RW_ADMINISTRATOR (vorhandenen Admin-User fuer die
  #     Reports-Oberflaeche berechtigen, damit Report-Jobs ueber EM verwaltet
  #     werden koennen - NICHT ueber "Users and Groups", der User existiert
  #     bereits, nur die Rolle fehlt):
  #   EM -> WebLogic Domain (WebLogic-Domaene) -> Security (Sicherheit) ->
  #         Application Roles (Anwendungsrollen)
  #   Application Stripe "reports" auswaehlen, mit ">" suchen
  #   Rolle RW_ADMINISTRATOR auswaehlen -> Edit (Bearbeiten)
  #   Bereich Members (Mitglieder) -> + Add (+ Hinzufuegen)
  #     Type (Typ): User (Benutzer), mit ">" suchen, weblogic auswaehlen -> OK
  #   Mit OK bestaetigen

  # 8.2 monUser -> RW_MONITOR (darf NUR den Status abfragen, keine Berichte).
  #     WICHTIG: Benutzer werden NICHT direkt unter "Users and Groups"
  #     angelegt, sondern innerhalb eines Security Realm (hier "myrealm") -
  #     ein haeufiger Stolperstein, wenn man den Menuepunkt direkt sucht:
  #   Benutzer anlegen:
  #     EM -> WebLogic Domain (WebLogic-Domaene) -> Security (Sicherheit) ->
  #           Security Realms (Sicherheitsbereiche) -> myrealm
  #     Tab Users and Groups (Benutzer und Gruppen) -> Create (Erstellen)
  #     Name monUser, Beschreibung, Passwort vergeben -> OK
  #   Rolle RW_MONITOR pruefen/zuweisen:
  #     EM -> WebLogic Domain (WebLogic-Domaene) -> Security (Sicherheit) ->
  #           Application Roles (Anwendungsrollen)
  #     Application Stripe "reports" auswaehlen, mit ">" suchen
  #     RW_MONITOR vorhanden? -> Edit (Bearbeiten) -> User monUser per
  #       + Add (+ Hinzufuegen) zuweisen
  #     Falls nicht vorhanden: Create (Erstellen) -> Name RW_MONITOR,
  #       Benutzer zuweisen
  #   Policy fuer RW_MONITOR verknuepfen:
  #     EM -> WebLogic Domain (WebLogic-Domaene) -> Security (Sicherheit) ->
  #           Application Policies (Anwendungsrichtlinien)
  #     Application Stripe "reports" auswaehlen, mit ">" suchen
  #     Prinzipal RW_MONITOR auswaehlen -> Edit (Bearbeiten)
  #     Pruefen, dass Rolle RW_MONITOR bereits als Prinzipal zugeordnet ist,
  #       sonst zuweisen
  #     Bereich Permissions (Berechtigungen) -> + Add (+ Hinzufuegen)
  #       Permission Class: oracle.reports.server.WebCommandPermission
  #       mit ">" suchen, Resource auswaehlen:
  #         webcommands=showmyjobs,getjobid,showjobid,getserverinfo,showjobs server=*
  #       Permission Actions: ALL -> OK -> OK

  # 8.3 RepRunner -> RW_EXECREPORTS (fuehrt Berichte tatsaechlich aus, kein
  #     Admin-Zugriff; dieser User wird anschliessend in cgicmd.dat
  #     hinterlegt, damit das Kennwort nicht im Report-Aufruf/der URL steht):
  #   Benutzer anlegen (wie 8.2 - Security Realms -> myrealm):
  #     EM -> WebLogic Domain (WebLogic-Domaene) -> Security (Sicherheit) ->
  #           Security Realms (Sicherheitsbereiche) -> myrealm
  #     Tab Users and Groups (Benutzer und Gruppen) -> Create (Erstellen)
  #     Name RepRunner, Beschreibung, starkes Passwort vergeben -> OK
  #   Rolle RW_EXECREPORTS anlegen:
  #     EM -> WebLogic Domain (WebLogic-Domaene) -> Security (Sicherheit) ->
  #           Application Roles (Anwendungsrollen)
  #     Application Stripe "reports" auswaehlen, mit ">" suchen
  #     Create (Erstellen) -> Name RW_EXECREPORTS, Benutzer RepRunner per
  #       + Add (+ Hinzufuegen) zuweisen -> OK
  #   Policy fuer RW_EXECREPORTS anlegen:
  #     EM -> WebLogic Domain (WebLogic-Domaene) -> Security (Sicherheit) ->
  #           Application Policies (Anwendungsrichtlinien)
  #     Application Stripe "reports" auswaehlen, mit ">" suchen
  #     Create (Erstellen) -> neuer Prinzipal RW_EXECREPORTS, Rolle
  #       RW_EXECREPORTS als Prinzipal zuweisen
  #     Bereich Permissions (Berechtigungen) -> + Add (+ Hinzufuegen)
  #       Permission Class: oracle.reports.server.ReportsPermission
  #       mit ">" suchen, Resource auswaehlen:
  #         report=* server=* destype=* desformat=* allowcustomargs=true
  #       Permission Actions: ALL -> OK -> OK

  # 8.4 Ausfuehrungsbenutzer in cgicmd.dat hinterlegen (ergaenzt Schritt 5).
  #     WICHTIG: authid muss NACH %2 stehen, nicht davor - sonst wird es
  #     nicht ausgewertet:
  sed -i 's/\(statusformat=xml\)/\1 %2 authid=RepRunner\/<REPRUNNER_PASSWORD>/' "$CGICMD_DAT"
  chmod 640 "$CGICMD_DAT"
  cat "$CGICMD_DAT"

  # Falls die neuen Rollen/Policies nicht sofort wirken (weiterhin 401/403
  # trotz korrektem authid): der Security-Cache des Managed Servers wird
  # erst nach einem Neustart aktualisiert.
  #   $DOMAIN_HOME/bin/stopManagedWebLogic.sh ${WLS_MANAGED_SERVER} ${WLS_ADMIN_URL}
  #   $DOMAIN_HOME/bin/startManagedWebLogic.sh ${WLS_MANAGED_SERVER} ${WLS_ADMIN_URL}

  # Verifikation (monUser, ohne Kennwort in einer geteilten Shell-History -
  # interaktiv eingeben statt fest zu verdrahten)
  curl -s "http://localhost:${WLS_REPORTS_PORT}/reports/rwservlet/getserverinfo?authid=monUser/<MONUSER_PASSWORD>&statusformat=XML"

           NICHT auf die exakte Versionsdatei

  Problem: RCU bricht mit "Schema already exists" ab
  Ursache: DB_SCHEMA_PREFIX kollidiert mit einer bereits vorhandenen
           Registrierung in der externen Datenbank
  Loesung: Anderen Prefix waehlen, oder (nur nach Ruecksprache mit dem
           DB-Team!) alte Schemas vorher per "rcu -silent -dropRepository"
           entfernen
           ACHTUNG: -dropRepository loescht auch den Tablespace der Schemas
           MIT Datendateien ("drop tablespace FMW_DATA including contents
           and datafiles") - auch wenn das DB-Team ihn angelegt hat! Vor
           dem neuen createRepository muss der Tablespace neu angelegt
           werden. Beim Drop KEINE -tablespace/-tempTablespace Parameter
           angeben (sonst Abbruch mit RCU-6197).

  Problem: Domain geloescht und neu angelegt - Configuration Wizard bzw.
           WLST bricht in der Phase "OPSS Processing" ab mit
           "The schema DEV_OPSS is already in use for security store(s)"
  Ursache: Das OPSS-Schema ist fest an die Domain gebunden, die es zuerst
           benutzt hat. Eine neue Domain kann es nicht uebernehmen.
  Loesung: Neue Domain = neue RCU-Schemas. Halb angelegtes Domain-
           Verzeichnis loeschen, Schemas per "rcu -silent -dropRepository"
           entfernen (nur nach Ruecksprache mit dem DB-Team, siehe oben:
           Tablespace wird mitgeloescht!), Tablespace neu anlegen, RCU
           neu ausfuehren, dann die Domain neu anlegen.

  Problem: Configuration Wizard bietet trotz bestehender Domain "Create
           Domain" statt "Update Domain" an, oder bricht mit einem
           Pfad-Konflikt ab
  Ursache: $DOMAIN_HOME/config/config.xml existiert bereits - der
           Assistent legt bei "Create Domain" eine komplett neue Domain an
  Loesung: VOR dem Start immer pruefen, ob $DOMAIN_HOME/config/config.xml
           schon existiert (siehe Hinweis in Schritt 4); im Assistenten
           dann "Update Domain" statt "Create Domain" waehlen, oder einen
           anderen DOMAIN_HOME verwenden

  Problem: Reports-Engine startet nicht / "status=0" (DEAD) im
           getserverinfo-Status
  Ursache: haeufig REPORTS_PATH/TNS_ADMIN falsch oder Datenbank nicht
           erreichbar
  Loesung: rwserver.conf-Umgebungsvariablen pruefen, DB-Konnektivitaet
           per "nc -zv $DB_HOST $DB_PORT" erneut testen

  Problem: Parameterformular / HTML-Ausgabe zeigt falsche Zeichen
           (Symbol/griechische Glyphen)
  Ursache: separates Font-Thema, nicht Teil dieses Kochbuchs
  Loesung: siehe Font_kochbuch_de.txt

  Problem: getserverinfo liefert weiterhin 401/403, obwohl Benutzer/Rolle/
           Policy in Schritt 8 korrekt angelegt wurden
  Ursache: der Security-Cache des Managed Servers uebernimmt neue
           Rollen/Policies nicht immer sofort
  Loesung: $WLS_MANAGED_SERVER neu starten (stopManagedWebLogic.sh,
           dann startManagedWebLogic.sh - siehe Schritt 8 Ende)
