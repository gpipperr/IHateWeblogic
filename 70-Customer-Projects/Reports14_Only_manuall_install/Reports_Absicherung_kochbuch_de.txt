WORUM GEHT ES - IN EINFACHEN WORTEN
--------------------------------------------------------------------------------

  Es gibt vier "Schluessel" mit eigenem Kennwort:

    Konto              wo es lebt              wofuer
    -----------------  ----------------------  ------------------------------
    cn=Admin           eingebettetes LDAP des  technischer Lese-Zugang: der

                       AdminServers            Reports-Server schaut damit
                                               die WebLogic-Benutzer nach
    monUser            WebLogic (myrealm)      NUR Status abfragen
                                               (getserverinfo, showjobs) -
                                               Rolle RW_MONITOR
    RepRunner          WebLogic (myrealm)      NUR Berichte ausfuehren - steht
                                               in cgicmd.dat - Rolle
                                               RW_EXECREPORTS
    repadmin           rwserver.conf           Notfall-Admin des Reports-
                       <identifier>            Servers (kein WebLogic-Konto)

  Dazu die Gruppe "Administrators" (alle WebLogic-Admins) mit der Rolle
  RW_ADMINISTRATOR.

  Das Problem: Der eigenstaendige Reports-Server ist ein eigenes Java-
  Programm ausserhalb von WebLogic. Er kennt die WebLogic-Benutzer von sich
  aus NICHT - er sucht sie in einer XML-Datei, in der sie nicht stehen.
  Folge ohne Absicherung:
    - Berichte laufen OHNE jede Benutzerpruefung (nur DB-Login),
    - Status-Abfragen gehen nur mit dem repadmin, monUser bekommt REP-52262.

  Die Loesung in drei Teilen:
    A) Der Reports-Server fragt das LDAP des AdminServers (dort stehen die
       WebLogic-Benutzer) - Anmeldung mit cn=Admin, dessen Kennwort im
       OPSS-Tresor (Credential Store) liegt.
    B) In rwserver.conf schaltet securityId="rwJaznSec" die Pruefung ein.
    C) Rollen und Berechtigungen (RW_MONITOR, RW_EXECREPORTS) verbinden die
       Benutzer mit dem, was sie duerfen.

  REIHENFOLGE IST WICHTIG: B) NIE ohne A) - sonst scheitert JEDE Anmeldung
  (REP-50171) und KEIN Bericht laeuft mehr.

  Abhaengigkeit: Das LDAP laeuft im AdminServer. Ist der AdminServer
  gestoppt, kann der Reports-Server niemanden anmelden (Berichte und
  Status-Abfragen schlagen fehl, bis er wieder laeuft).

SCHRITT 10: Das OVD-Problem - EM findet keine Benutzer
================================================================================

  # SYMPTOM: Im Enterprise Manager unter Security -> Application Roles ->
  # Rolle bearbeiten -> "Add Principal" bleibt die Benutzersuche LEER,
  # obwohl die Benutzer existieren.
  #
  # URSACHE (auf dem Testsystem nachgewiesen, 2026-10-16): Die Benutzersuche
  # im EM laeuft ueber "libOVD" mit der Konfiguration in
  #   $DOMAIN_HOME/config/fmwconfig/ovd/default/adapters.os_xml
  # Der eigenstaendige Reports-Server benutzt bei seinem Start DIESELBE
  # Datei, schreibt sie mit seinem eigenen Stand neu und laesst eine
  # Sperrdatei ovd.lok liegen. Danach fehlt dem EM die Verbindung zum
  # WebLogic-Benutzerverzeichnis. Es ist ein Anzeige-Problem des EM - die
  # Anmeldung der Benutzer und die Absicherung des Reports-Servers
  # funktionieren trotzdem. Der LibOVD-Patch des CPU Oktober 2026
  # (39726399) behebt es NICHT; Oracle kennt keinen Patch (SR in
  # Vorbereitung).

  # 10.1 Umgehung 1 - einfach und immer moeglich: Rollen per WLST zuweisen
  #      (Schritt 4.3). Das ist der empfohlene Weg.

  # 10.2 Umgehung 2 - in der Oberflaeche: im Dialog "Add Principal" das
  #      Feld "Advanced Option" (Erweiterte Option) anhaken und den
  #      Benutzernamen (z.B. monUser) von Hand eintragen, ohne Suche.

  # 10.3 Wenn die EM-Suche gebraucht wird (Wiederherstellen, bis zum
  #      naechsten Neustart des Reports-Servers):
  #      a) AdminServer stoppen (Managed Server und Reports-Server laufen
  #         weiter):
  $DOMAIN_HOME/bin/stopWebLogic.sh
  #      b) Sperrdatei wegschieben:

  mv $OVD/ovd.lok $OVD/ovd.lok.$(date +%Y%m%d_%H%M%S) 2>/dev/null; ls -la $OVD
  #      c) AdminServer starten:

  nohup $DOMAIN_HOME/bin/startWebLogic.sh > /tmp/adminserver_start.out 2>&1 &
  #         ...warten bis "RUNNING" (tail -f /tmp/adminserver_start.out)
  #      d) im EM SOFORT einmal "Add Principal" -> Suche ausfuehren. Danach
  #         behaelt der AdminServer die richtige Konfiguration im Speicher,
  #         auch wenn der Reports-Server die Datei spaeter wieder
  #         ueberschreibt - bis zum naechsten AdminServer-Neustart.
  #      Mit Autostart (systemd): AdminServer-Neustart ueber die Unit ist
  #      ein Komplett-Neustart, dabei startet der Reports-Server nach dem
  #      AdminServer und ueberschreibt die Datei VOR der ersten Suche -
  #      deshalb den AdminServer hier einzeln wie oben neu starten.

  # 10.4 NICHT tun: die Variable DO_NOT_PUSH_DATA_LIBOVD oder andere
  #      Oracle-interne Schalter setzen - ungetestet, nur nach Freigabe
  #      durch Oracle Support.
