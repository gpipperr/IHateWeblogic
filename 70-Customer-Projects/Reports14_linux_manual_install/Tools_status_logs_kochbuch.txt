================================================================================
  Werkzeuge fuer den Betrieb: Status und Logs auf einen Blick
  (Kleine Skripte, OHNE IHateWeblogic-Skripte/Lib als Abhaengigkeit)
================================================================================
  Zielgruppe : Kunde / Betrieb - schnell sehen, ob alles laeuft, und bei
               Problemen die passenden Logzeilen finden
  Umgebung   : Oracle Linux 9, FMW 14.1.2.0.0, WebLogic 14.1.2, nur Reports
  Erstellt   : 2026-10, neu gefasst 2026-11-04 (eine ini, setdb,
               Stil nach 70-Customer-Projects/cookbook-Skill.md)
  Voraussetz.: Reports_kochbuch_de.txt vollstaendig durchgefuehrt;
               Fahrplan ../Start_beim_Kunden_kochbuch_de.txt Schritte 1-3
               (Tools abgelegt, setdb aktiv, patch_install.ini angepasst);
               fuer den Node-Manager-Status: gespeicherte Zugangsdaten
               aus Autostart_linux_middleware.txt Schritt 1c

  Die Skripte liegen im Repository unter
    70-Customer-Projects/tools/bash/
  und werden unveraendert nach /u01/oracle/tools/ kopiert (Fahrplan
  Schritt 1). Sie benutzen nur Standard-Werkzeuge (bash, ss, ps, curl,
  find, tail, grep) und das mitgelieferte wlst.sh - keine weiteren
  Skripte, keine Kennwoerter.

    status.sh           Zustand in drei Stufen: Ports (ss), Prozesse (ps),
                        Status ueber HTTP und den Node Manager (WLST)
    show_log.sh         das aktuelle Log EINER Komponente (Auswahl-Menue)
    show_all_logs.sh    alle aktuellen Logs der Domain live mitlesen
    show_errors.sh      nur die Fehlerzeilen aus diesen Logs
    set_script_env.sh   laedt patch_install.ini in die Sitzung
                        (fuer die Kochbuch-Befehle)

  Alle vier Betriebs-Skripte lesen ihre Werte selbst aus
  patch_install.ini im eigenen Verzeichnis - kein vorheriges Laden noetig.
================================================================================

SCHRITT 2: Werte fuer die Tools in patch_install.ini pruefen  (als oracle)
================================================================================

  . /u01/oracle/tools/set_script_env.sh

  set_script_env_show | grep -E 'DOMAIN|ADMIN|MANAGED|REPORTS_SERVERS|NODEMANAGER|NM_|EXTRA|LOG_MIN'

  # Erwartet (Beispiel):
  #   DOMAIN_NAME                  reportRpgpi
  #   DOMAIN_HOME                  /u01/user_projects/domains/reportRpgpi
  #   WLS_ADMIN_PORT               7001
  #   WLS_NODEMANAGER_PORT         5556
  #   ADMIN_SERVER                 AdminServer
  #   MANAGED_SERVERS              WLS_REPORTS:9002   (Name:Port, mehrere moeglich)
  #   REPORTS_SERVERS              repServer01        (mehrere durch Leerzeichen)
  #   NM_HOST / NM_TYPE            localhost / plain
  #   EXTRA_PORTS                  80 443   (Nginx; leer lassen, wenn nicht benoetigt)
  #   LOG_MINUTES                  60

  grep -m1 -o '<name>[^<]*' $DOMAIN_HOME/config/config.xml

  # Erwartet: <name>reportRpgpi  (= DOMAIN_NAME)

  # Weicht etwas ab:
  vi /u01/oracle/tools/patch_install.ini

  # In patch_install.ini stehen KEINE Kennwoerter.

SCHRITT 3: Zugangsdaten fuer den Node-Manager-Status pruefen  (als oracle)

  # status.sh fragt den echten Zustand beim Node Manager ab - mit den
  # Zugangsdaten, die einmalig mit storeUserConfig gespeichert wurden

================================================================================
SCHRITT 4: Status abfragen  (als oracle)
================================================================================

  status.sh

  # alle drei Stufen, ca. 10 Sekunden

  status.sh -q

  # schnell: ohne Node-Manager-Abfrage
  # Erwartet (alles in Ordnung):
  #
  # --- Stufe 1: Ports (ss) -------------------------------------------
  #   NodeManager      Port 5556   LISTEN   127.0.0.1:5556
  #   AdminServer      Port 7001   LISTEN   127.0.0.1:7001
  #   WLS_REPORTS      Port 9002   LISTEN   127.0.0.1:9002
  #
  # --- Stufe 2: Prozesse (ps) ----------------------------------------
  #   Komponente       PID      Laufzeit     RAM MB   gestartet von
  #   NodeManager      2078     01:00:50     181      -
  #   AdminServer      2350     01:00:35     2001     Node Manager
  #   WLS_REPORTS      3689     59:37        2278     Node Manager
  #   repServer01      3967     59:16        416      Node Manager  Engines: 2
  #
  # --- Stufe 3: Status (HTTP /weblogic/ready, Node Manager) ---------
  #   HTTP AdminServer      200 = RUNNING
  #   HTTP WLS_REPORTS      200 = RUNNING
  #   NM   AdminServer      RUNNING
  #   NM   WLS_REPORTS      RUNNING
  #   NM   repServer01      RUNNING
  #
  # --- Zusammenfassung -----------------------------------------------
  #   Komponente       Port     Prozess  HTTP     NodeMgr    Ergebnis
  #   ...
  # Ergebnis: alles in Ordnung

  # Was die Stufen bedeuten:
  #   Stufe 1  Port offen?  -> der Dienst nimmt Verbindungen an
  #   Stufe 2  Prozess da?  -> laeuft er, seit wann, wie viel Speicher;
  #            "gestartet von Node Manager" ist richtig. "Skript (Node
  #            Manager kennt ihn nicht!)" heisst: von Hand gestartet -
  #            dann sieht ihn der Node Manager als SHUTDOWN (siehe
  #            BEKANNTE PROBLEME)
  #            Engines = Anzahl der Reports-Engine-Prozesse
  #   Stufe 3  200 = Server meldet sich bereit, 503 = startet noch;
  #            NM = was der Node Manager ueber den Server weiss
  #            (RUNNING, STARTING, SHUTDOWN, FAILED_NOT_RESTARTABLE ...)

  # Rueckgabewert (z.B. fuer eine Ueberwachung):

  status.sh -q > /dev/null

  echo "Rueckgabewert: $?"

  # Erwartet: 0 = in Ordnung, 1 = Warnung, 2 = Fehler


================================================================================
SCHRITT 4b: Das Log einer Komponente oeffnen  (als oracle)
================================================================================

  # Ohne Parameter fragt das Skript, welche Komponente und welches Log -
  # angeboten werden nur die Komponenten aus patch_install.ini und nur
  # Logs, die es wirklich gibt:

  show_log.sh

  # Erwartet:
  #   Welche Komponente?
  #   1) NodeManager
  #   2) AdminServer
  #   3) WLS_REPORTS
  #   4) repServer01
  #   Nummer: 3
  #   Welches Log von WLS_REPORTS?
  #   1) log       Server-Log (WebLogic-Meldungen)
  #   2) out       Konsolen-Ausgabe (Start, stdout/stderr)
  #   3) diag      Diagnose-Log (FMW: Sicherheit, Reports, JRF)
  #   4) rwservlet rwservlet-Log (Reports-Aufrufe)
  #   Nummer: 1

  # Oder direkt (Gross-/Kleinschreibung egal):

  show_log.sh nodemanager

  show_log.sh adminserver

  # Auswahl der Logs des AdminServers

  show_log.sh AdminServer out

  # direkt die Konsolen-Ausgabe

  show_log.sh reports

  # Reports-Server (log | out | engine)

  show_log.sh reports engine

  # das zuletzt geschriebene Engine-Log

  # Standard: live mitlesen (tail -F, die letzten 50 Zeilen zuerst,
  # Strg+C beendet). Zum Blaettern und Suchen in less oeffnen:

  show_log.sh -l reports

  # less: G = Ende, /text = suchen, F = live, q = beenden

  show_log.sh -n 300 adminserver log

  # mit den letzten 300 Zeilen beginnen


================================================================================
SCHRITT 5: Logs live mitlesen  (als oracle)
================================================================================

  # Alle Logs, die in der letzten Stunde geschrieben wurden (WebLogic,
  # Reports-Server und -Engines, Node Manager, Enterprise Manager) - erst
  # die Liste der Dateien, dann je Datei die letzten 20 Zeilen und danach
  # alles Neue live. Beenden mit Strg+C.

  show_all_logs.sh

  show_all_logs.sh -m 240

  # letzte 4 Stunden

  show_all_logs.sh -n 100

  # mehr Zeilen je Datei

  # Ohne Skript - derselbe Befehl von Hand:
  #   find $DOMAIN_HOME/servers $DOMAIN_HOME/nodemanager $DOMAIN_HOME/sysman/log \
  #        -type f \( -name "*.log" -o -name "*.out" -o -name "*.trc" \) \
  #        ! -name "access.log*" ! -name "*.lck" -mmin -60 -print0 \
  #     | xargs -0 tail -F -n 20


================================================================================
SCHRITT 6: Nur die Fehler anzeigen  (als oracle)
================================================================================

  # Neue Fehler ab jetzt live (Strg+C beendet). Vor jedem Fehler steht,
  # aus welcher Logdatei er kommt:

  show_errors.sh

  # Erst die letzten Fehler (max. 50) der letzten Stunde, dann live weiter:

  show_errors.sh -r

  show_errors.sh -r -m 1440

  # letzte 24 Stunden

  # Gesucht wird nach:
  #   <Error> <Critical>  ERROR  SEVERE  Exception  REP-nnnnn  JPS-nnnnn  BEA-nnnnnn
  # Das Muster steht oben im Skript (PATTERN=...) und kann angepasst werden.
  #
  # Typischer Ablauf bei einem Problem:
  #   1. status.sh                  -> welche Komponente hat ein Problem?
  #   2. show_errors.sh -r          -> was steht dazu in den Logs?
  #   3. show_all_logs.sh           -> Zusammenhang rund um den Fehler


================================================================================
BEKANNTE PROBLEME UND LOESUNGEN
================================================================================

  Problem: status.sh meldet "Node Manager: keine gespeicherten
           Zugangsdaten gefunden"
  Ursache: ~/oracle-WebLogicConfig.properties / ~/oracle-WebLogicKey.properties
           fehlen oder gehoeren einem anderen Benutzer
  Loesung: Schritt 3 (storeUserConfig) als oracle ausfuehren

  Problem: status.sh meldet "Node Manager: Anmeldung fehlgeschlagen"
           (z.B. BadPaddingException oder "Access to domain ... denied")
  Ursache: gespeicherte Zugangsdaten passen nicht (mehr) zum Node Manager,
           z.B. nach einer Kennwortaenderung
  Loesung: Autostart_linux_middleware.txt Schritt 1b/1c - Zugangsdaten
           pruefen und neu speichern

  Problem: Stufe 2 zeigt "Skript (Node Manager kennt ihn nicht!)",
           Stufe 3 NM zeigt SHUTDOWN, obwohl der Server laeuft
  Ursache: Server wurde von Hand mit startWebLogic.sh /
           startManagedWebLogic.sh gestartet, nicht ueber den Node Manager
           bzw. den Autostart
  Loesung: Server normal stoppen und ueber den Autostart starten
           (systemctl, Autostart_linux_middleware.txt) - sonst ueberspringt
           ihn der Node Manager beim Stoppen und ein Neustart scheitert am
           belegten Port

  Problem: Stufe 3 HTTP meldet 503
  Ursache: Server startet noch (oder haengt im Start)
  Loesung: 1-2 Minuten warten; bleibt es bei 503: show_errors.sh -r

  Problem: show_all_logs.sh / show_errors.sh zeigen eine neue Logdatei nicht
  Ursache: tail -F folgt nur den Dateien, die beim Aufruf schon da waren
           (auch ueber eine Rotation hinweg) - neu angelegte Dateien, z.B.
           nach einem Neustart, kommen nicht dazu
  Loesung: Skript beenden (Strg+C) und neu aufrufen

  Problem: "FEHLER: .../patch_install.ini nicht gefunden"
  Ursache: patch_install.ini liegt nicht neben den Skripten
  Loesung: Fahrplan Schritt 3 - oder fuer einen Test eine andere Datei:
           IHW_INI=/pfad/datei.ini status.sh

  Problem: "Bitte mit Punkt aufrufen" beim Aufruf von set_script_env.sh
  Ursache: ohne Punkt laeuft das Skript in einer eigenen Shell - die
           Werte waeren danach sofort wieder weg
  Loesung: ". /u01/oracle/tools/set_script_env.sh" (Punkt, Leerzeichen, Pfad)

  Problem: "status.sh: command not found" / Kurzbefehl "wlst" / "domain"
           unbekannt
  Ursache: setdb nicht eingerichtet oder noch keine neue Shell geoeffnet
           ("domain" und "wlst" kennen erst nach "setdb" ein DOMAIN_HOME)
  Loesung: Fahrplan Schritt 2, dann setdb und den Domain-Eintrag waehlen

  Problem: "Keine Logdatei in den letzten 60 Minuten geschrieben"
  Ursache: Umgebung laeuft schon laenger ruhig, oder DOMAIN_HOME in
           patch_install.ini falsch
  Loesung: Zeitraum vergroessern (-m 1440) bzw. SCHRITT 2
