  BENUTZERKONTEN DER ENTWICKLER  [live 2026-10-27]
  ------------------------------------------------
  Mit einem normalen Benutzerkonto (ohne Admin-Rechte) laesst sich der
  Builder nach der Installation NICHT starten:
  - Der Oracle-Installer bricht beim Installieren die Rechte-Vererbung
    unter E:\oracle (setzt eigene, explizite Rechte auf die Unterordner).
  - Eine Gruppe, die man auf E:\oracle berechtigt (z.B. "Reports-
    Entwickler", Lesen/Ausfuehren), kommt deshalb in den Unterordnern
    nicht an.
  - Die Rechte muessten Ordner fuer Ordner von Hand gesetzt werden - sehr
    aufwendig, fehleranfaellig und nach Patches erneut zu pruefen
    (Annahme: OPatch legt Dateien mit den Rechten des Installationskontos
    an).
  Entscheidung: Die Entwickler arbeiten per RDP mit einem Konto mit
  LOKALEN ADMINISTRATOR-RECHTEN auf diesem Server.
  - Je Entwickler ein EIGENES Konto (persoenlich, nicht ORASYSTEM teilen),
    Mitglied der lokalen Gruppe "Administratoren".
  - Der Server dient nur der Builder-Entwicklung (keine Produktion, keine
    weiteren Dienste); Zugriff nur per RDP aus dem Admin-/Entwicklernetz.
  - Lizenz-Nebeneffekt: Windows Server erlaubt 2 gleichzeitige
    Admin-RDP-Sitzungen OHNE RDS-Lizenzen - passt fuer 2 Entwickler; ab dem
    dritten gleichzeitigen Benutzer RDS-Lizenzierung beim Kunden klaeren.

  Regeln:
  - Pfade OHNE Leerzeichen und kurz halten (Windows: lange
    Umgebungsvariablen brechen Reports - Oracle Install 12.2.1.3 Anhang B.3).
  - Rechnername und IP nach der Installation NICHT mehr aendern.
  - Englisches Windows bevorzugen (Fehlermeldungen fuer Oracle Support).
  - Virenschutz: Ausnahme fuer E:\oracle waehrend Installation und Patchen
    (Patch-READMEs: "anti-virus software should be temporarily stopped").

  rem     Builder schliessen, Junction neu setzen

  E:\Java\jdk-21\bin\java -version

  rem 1.4 JAVA_HOME systemweit (neue cmd-Shell danach oeffnen)

  rem     unkritisch, aber wie auf dem Linux-Server einheitlich)
  rem     E:\Java\jdk-21\conf\security\java.security:
  rem       securerandom.source=file:/dev/./urandom

  rem 1.6 Datenbank erreichbar? (vom Windows Server aus)

SCHRITT 10: Betrieb, Patchen, bekannte Probleme
================================================================================

  Patchen: bei jedem Patchzyklus dieselben Nummern wie auf dem
  Linux-Server, in der Windows-Variante (Schritt 4). Vorher alle
  Builder-Sitzungen beenden. JDK-Update: neues JDK nach E:\Java,
  Junction E:\Java\jdk-21 umsetzen (Schritt 1.3).

  Der AdminServer muss im Alltag NICHT laufen. Er wird nur gebraucht, um
  eine weitere Tools-Instanz anzulegen oder die Domain zu aendern.

  RCU-Datenbank im Alltag  [gemessen 2026-10-27, Builder-GUI beim Kunden pruefen]
  - Die Reports-Werkzeuge nutzen die RCU-Schemas zur Laufzeit NICHT:
    Messung mit strace auf dem Linux-Testsystem (rwconverter, gleiche
    Laufzeit und gleiche Tools-Instanz wie der Builder) - keine OPSS-/
    Wallet-Datei geoeffnet, keine Verbindung zum AdminServer, als einzige
    DB-Verbindung die Anmeldung des Berichts selbst.
  - Gebraucht wird die RCU-Datenbank nur fuer: Domain aendern, weitere
    Tools-Instanz anlegen, AdminServer starten - und fuer ein spaeteres
    Versions-Upgrade (Upgrade Assistant aktualisiert Schemas UND Domain;
    ohne Schemas = Neuinstallation). OPatch-Patches brauchen sie nicht.
  - Eigene RCU-DB auf diesem Server: Schemas und DB behalten, den
    DB-Dienst aber auf Starttyp "Manuell" stellen - spart RAM fuer die
    RDP-Sitzungen. Nur fuer Domain-Aenderungen / Upgrade starten:
      sc config OracleService<SID> start= demand
      net stop OracleService<SID>        (bzw. net start ... bei Bedarf)
  - Einmal pruefen (Builder-GUI ist noch nicht gemessen): DB-Dienst
    stoppen, rwbuilder.bat starten, mit der Anwendungs-DB verbinden,
    Vorschau erzeugen. Klappt das, ist es bestaetigt.
  - Profil RCU_USER (kein Kennwortablauf) fuer RWDEV_* trotzdem setzen -
    ein abgelaufenes Konto faellt sonst erst auf, wenn der AdminServer
    gebraucht wird.

  Problem: Builder startet mit einem normalen Benutzerkonto nicht, auch
           wenn eine Gruppe auf E:\oracle Lese-/Ausfuehrrechte hat
  Ursache: der Oracle-Installer bricht die Rechte-Vererbung unter E:\oracle
           (explizite Rechte je Unterordner) - die Gruppe kommt unten nicht
           an  [live 2026-10-27]
  Loesung: Entwickler-Konten als lokale Administratoren (Voraussetzungen,
           "Benutzerkonten"); Rechte von Hand je Ordner zu setzen ist nicht
           empfohlen (aufwendig, nach Patches erneut)

  Problem: "MSVCP100.dll wurde nicht gefunden" beim Start des Builders
  Loesung: Visual C++ Redistributable x64 UND x86 installieren (Schritt 1)

  Problem: AdminServer startet nicht (fuer Domain-Aenderung / Upgrade),
           Fehler zu OPSS / Datenbank
  Ursache: RCU-DB-Dienst nicht gestartet, Kennwort eines RWDEV_*-Schemas
           abgelaufen oder Konto gesperrt
  Loesung: DB-Dienst starten; DB-Team: Profil RCU_USER, Konto entsperren
           (Schritt 5)

  Problem: Vorschau im Builder sieht anders aus als die PDF vom Server
  Ursache: andere Fonts / uifont.ali als auf dem Linux-Server
  Loesung: Schritt 8.3, Font_kochbuch_de.txt

  Problem: Reports-Fehler wegen zu langer Pfade / Umgebungsvariablen
  Ursache: Windows-Grenze fuer Umgebungsvariablen (Oracle Install 12.2.1.3
           Anhang B.3)
  Loesung: kurze Pfade ohne Leerzeichen, PATH nicht unnoetig verlaengern

  Problem: Bericht laeuft im Builder, auf dem Server nicht
  Ursache: unterschiedlicher Patchstand Builder / Server, andere
           Verbindungs-Aliase, Bilder/Bibliotheken nicht im REPORTS_PATH des
           Servers
  Loesung: lspatches beider Seiten vergleichen; tnsnames und Pfade abgleichen
