==========================================================================
  Kochbuch: GitLab-Pipelines fuer Oracle Reports einrichten
            deploy_dev  (Push auf main     -> DEV-Reports-Server)
            deploy_prod (Tag prod-*        -> PROD-Reports-Server)
==========================================================================
  Zielgruppe : GitLab-Administrator (Einstellungen, Runner) und
               Linux-Administrator der beiden Reports-Server (Benutzer oracle)
  Umgebung   : selbst gehostetes GitLab, ein GitLab-Runner mit bash/git/ssh,
               zwei Linux-Server mit Oracle Reports 14.1.2 (DEV und PROD),
               Entwickler-PCs mit dem Repository oracle-report (Windows)
  Erstellt   : 2026-11-12
  Grundlage  : IHateWeblogic/70-Customer-Projects/Reports14_builder_windows/
                 Git_deploy.md        (Konzept, Abschnitte 2 bis 7)
                 deploy/ci_deploy.sh  (der Pipeline-Job)
                 deploy/rwdeploy.sh   (Warteschlange auf dem Server)
                 deploy/template.gitlab-ci.yml
                 deploy/rwdeploy.conf.template
                 deploy/authorized_keys.example
                 scripts/README_DE.md (Arbeitsablauf der Entwickler)
  Wichtig    : - Reihenfolge einhalten: erst Server (SCHRITT 1-3), dann
                 GitLab (SCHRITT 4-5), ZULETZT die Datei .gitlab-ci.yml ins
                 Repository (SCHRITT 6). Der Push in SCHRITT 6 startet schon
                 die erste Pipeline.
               - Der private Schluessel gehoert NUR in die GitLab-Variable -
                 nie ins Repository, nie in eine Mail, nie in ein Ticket.
               - Auf den Servern wird nie etwas geloescht. Jede ersetzte
                 Datei liegt danach in der Sicherung (backup/<auftrag>/).
==========================================================================

SO LAEUFT ES (Ueberblick)
-------------------------

  Entwickler: checkin.ps1 --push--> GitLab main --Job deploy_dev--> DEV
  Entwickler: release_tag.ps1 --Tag prod-...--> GitLab --Job deploy_prod--> PROD

  Der Job laeuft auf dem GitLab-Runner, baut ein tar mit den Dateien und
  schickt es per SSH an rwdeploy.sh auf dem Server. rwdeploy.sh prueft das
  tar, kopiert die Dateien in die Reports-Ordner (mit Sicherung) und meldet
  das Ergebnis zurueck - die Pipeline wird gruen oder rot.

  Netz: nur Runner -> Server, Port 22 (SSH). Die Server rufen GitLab nie auf.

SCHRITT 0: Variablen setzen und pruefen  (als oracle, auf dem Server)
==========================================================================

  In JEDER neuen Sitzung auf einem Reports-Server zuerst diese Zeilen.
  RWD_ENV ist dev auf dem DEV-Server und prod auf dem PROD-Server.

  whoami
  # Erwartet: oracle

  hostname -f
  # Erwartet: der Name dieses Servers - DEV oder PROD? Pruefen!

  export RWD_ENV=dev
  # Auf dem PROD-Server:  export RWD_ENV=prod

  export RWD_HOME=/u01/app/oracle/rwdeploy

  export RWD_BIN=$RWD_HOME/bin

  export RUNNER_IP=<IP des GitLab-Runners aus V.2>

  echo "RWD_ENV=$RWD_ENV  RWD_HOME=$RWD_HOME"
  # Erwartet z.B.: RWD_ENV=dev  RWD_HOME=/u01/app/oracle/rwdeploy

  echo "RWD_BIN=$RWD_BIN  RUNNER_IP=$RUNNER_IP"
  # Erwartet z.B.: RWD_BIN=/u01/app/oracle/rwdeploy/bin  RUNNER_IP=<runner-ip>
  # Ein Wert LEER oder noch <...>? -> Zeile oben korrigieren.

SCHRITT 1: DEV-Server - rwdeploy.sh einrichten  (als oracle)
==========================================================================

  ---------------------------------------------------
  1.1 Brauche ich diesen Schritt?
  ---------------------------------------------------

  ls -l $RWD_BIN/rwdeploy.sh
  # "No such file or directory"        -> neu einrichten, weiter mit 1.2
  # Datei vorhanden                    -> Version pruefen:

  grep -c 'Reports/source' $RWD_BIN/rwdeploy.sh
  # 0                 -> aktuelle Version; nur 1.4 bis 1.6 pruefen
  # 1 oder mehr       -> ALTE Version (erwartet Ordner Reports/...) - sie
  #                      lehnt die Lieferungen ab ("path not allowed").
  #                      Sichern und mit 1.2 / 1.3 ersetzen:

  cp -p $RWD_BIN/rwdeploy.sh $RWD_BIN/rwdeploy.sh.bak

  ---------------------------------------------------
  1.2 Dateien auf den Server bringen
  ---------------------------------------------------

  mkdir -p $HOME/rwdeploy_install

  # Jetzt vom PC aus (z.B. WinSCP oder scp) diese zwei Dateien nach
  # $HOME/rwdeploy_install/ kopieren:
  #   deploy/rwdeploy.sh
  #   deploy/rwdeploy.conf.template
  # Uebertragung im Binaer-Modus (keine Zeilenende-Umwandlung).

  ls -l $HOME/rwdeploy_install
  # Erwartet: rwdeploy.sh und rwdeploy.conf.template

  file $HOME/rwdeploy_install/rwdeploy.sh
  # Erwartet: "Bourne-Again shell script, ASCII text executable"
  # Steht dort "with CRLF line terminators": falsch uebertragen ->
  # erneut im Binaer-Modus kopieren.

  ---------------------------------------------------
  1.3 Ordner anlegen und Skript ablegen
  ---------------------------------------------------

  mkdir -p $RWD_BIN

  cp $HOME/rwdeploy_install/rwdeploy.sh $RWD_BIN/

  chmod 750 $RWD_BIN/rwdeploy.sh

  bash -n $RWD_BIN/rwdeploy.sh
  # Erwartet: keine Ausgabe (= Syntax in Ordnung)

  ---------------------------------------------------
  1.4 Ziel-Ordner herausfinden und eintragen
  ---------------------------------------------------

  Die Berichte muessen in einen Ordner, aus dem der Reports-Server liest.
  Das steht in rwserver.conf unter <folderAccess><read>.

  ls $DOMAIN_HOME/config/fmwconfig/components/ReportsServerComponent/
  # Erwartet: der Name Ihres Reports-Servers, z.B. repserver01
  # DOMAIN_HOME leer? -> export DOMAIN_HOME=<Domain-Ordner>, z.B.
  #                      /u01/app/oracle/domains/fr_domain

  export RW_SERVER=<Name aus der Zeile oben>

  RW_CONF=$DOMAIN_HOME/config/fmwconfig/components/ReportsServerComponent/$RW_SERVER/rwserver.conf

  ls -l $RW_CONF
  # Erwartet: die Datei rwserver.conf (No such file -> RW_SERVER pruefen)

  grep -A2 '<folderAccess>' $RW_CONF
  # Erwartet z.B.:
  #   <folderAccess>
  #      <read>/u01/reports/source;/u01/reports/images</read>
  #   </folderAccess>
  # -> der Ordner fuer die .rdf und der fuer die Bilder. Notieren.
  # Kein <folderAccess>? -> REPORTS_PATH pruefen:

  grep REPORTS_PATH $DOMAIN_HOME/reports/bin/reports.sh
  # Erwartet: eine Zeile mit den Ordnern, getrennt durch ":"

  cp $HOME/rwdeploy_install/rwdeploy.conf.template $RWD_BIN/rwdeploy.conf

  vi $RWD_BIN/rwdeploy.conf

  # In vi die drei Zeilen pruefen - im Template stehen schon die
  # Standard-Ordner; nur aendern, wenn folderAccess etwas anderes zeigt
  # (Cursor auf den Wert,  cw  oder  i ):
  #   SPOOL_DIR="/u01/app/oracle/rwdeploy"        = $RWD_HOME
  #   TARGET_SOURCE_DIR="/u01/reports/source"     Ordner der .rdf
  #   TARGET_IMAGE_DIR="/u01/reports/images"      Ordner der Bilder
  # MAX_TAR_MB=100 so lassen.
  # Dann  Esc  und  :wq  (speichern und beenden).

  grep -v '^#' $RWD_BIN/rwdeploy.conf
  # Erwartet z.B.:
  #   SPOOL_DIR="/u01/app/oracle/rwdeploy"
  #   TARGET_SOURCE_DIR="/u01/reports/source"
  #   TARGET_IMAGE_DIR="/u01/reports/images"
  #   MAX_TAR_MB=100

  ls -ld /u01/reports/source /u01/reports/images
  # (Ihre Werte aus rwdeploy.conf einsetzen)
  # Erwartet: beide Ordner vorhanden, Besitzer oracle (oder Schreibrecht
  # fuer oracle). Fehlt einer: STOP - mit dem Reports-Administrator klaeren,
  # NICHT einfach anlegen (der Reports-Server muss ihn kennen).

  ---------------------------------------------------
  1.5 Skript lokal testen
  ---------------------------------------------------

  $RWD_BIN/rwdeploy.sh
  # Erwartet:
  #   ERROR: usage: enqueue <sha> <delta|tag|snapshot> | status <sha> [--wait N] | last | list | work
  # (= Skript laeuft und liest rwdeploy.conf)
  # "config not found" -> 1.4 pruefen.

  $RWD_BIN/rwdeploy.sh last
  # Erwartet: none   (= noch nie etwas verteilt)

  $RWD_BIN/rwdeploy.sh list

SCHRITT 3: Deploy-Schluessel  (als oracle, je Server einmal)
==========================================================================

  Jeder Server bekommt sein eigenes Schluesselpaar:
  - der oeffentliche Teil kommt in authorized_keys dieses Servers und
    darf dort NUR rwdeploy.sh starten, NUR vom Runner aus;
  - der private Teil kommt in die GitLab-Variable DEPLOY_SSH_KEY dieser
    Umgebung (SCHRITT 5.3) und wird danach auf dem Server geloescht.

  Erst fuer DEV (RWD_ENV=dev), dann fuer PROD (RWD_ENV=prod).

  ---------------------------------------------------
  3.1 Variablen pruefen
  ---------------------------------------------------

  echo "RWD_ENV=$RWD_ENV  RWD_HOME=$RWD_HOME  RUNNER_IP=$RUNNER_IP"
  # Leer? -> erst SCHRITT 0.

  ---------------------------------------------------
  3.2 Schluesselpaar erzeugen
  ---------------------------------------------------

  mkdir -p $RWD_HOME/keys

  chmod 700 $RWD_HOME/keys

  cd $RWD_HOME/keys

  ssh-keygen -t ed25519 -N '' -C gitlab-deploy-$RWD_ENV -f ./gitlab-deploy-$RWD_ENV
  # Erwartet:
  #   Generating public/private ed25519 key pair.
  #   Your identification has been saved in ./gitlab-deploy-dev
  #   Your public key has been saved in ./gitlab-deploy-dev.pub

  ls -l $RWD_HOME/keys
  # Erwartet: gitlab-deploy-dev (privat) und gitlab-deploy-dev.pub

  ---------------------------------------------------
  3.3 Zeile fuer authorized_keys vorbereiten
  ---------------------------------------------------

  PUBKEY=$(cat $RWD_HOME/keys/gitlab-deploy-$RWD_ENV.pub)

  echo "$PUBKEY"
  # Erwartet: ssh-ed25519 AAAA... gitlab-deploy-dev

  printf 'command="%s",restrict,from="%s" %s\n' "$RWD_BIN/rwdeploy.sh" "$RUNNER_IP" "$PUBKEY" > $RWD_HOME/keys/authorized_keys_zeile.txt

  cat $RWD_HOME/keys/authorized_keys_zeile.txt
  # Erwartet (EINE Zeile):
  #   command="/u01/app/oracle/rwdeploy/bin/rwdeploy.sh",restrict,from="<runner-ip>" ssh-ed25519 AAAA... gitlab-deploy-dev
  # Bedeutung:
  #   command=  jede Anmeldung mit diesem Schluessel startet nur rwdeploy.sh
  #   restrict  keine Shell, keine Weiterleitungen
  #   from=     nur vom Runner (IP aus V.2)

  ---------------------------------------------------
  3.4 Zeile in authorized_keys eintragen
  ---------------------------------------------------

  mkdir -p $HOME/.ssh

  chmod 700 $HOME/.ssh

  grep -c "gitlab-deploy-$RWD_ENV" $HOME/.ssh/authorized_keys
  # 0 oder "No such file"   -> weiter mit dem naechsten Befehl
  # 1                       -> alte Zeile vorhanden: in vi zuerst diese
  #                            Zeile loeschen ( dd ), dann wie unten

  vi $HOME/.ssh/authorized_keys

  # In vi:  G  (ans Dateiende), dann
  #   :r /u01/app/oracle/rwdeploy/keys/authorized_keys_zeile.txt
  # (fuegt die vorbereitete Zeile ein - nichts von Hand tippen)
  # Dann  Esc  und  :wq .

  chmod 600 $HOME/.ssh/authorized_keys

  grep "gitlab-deploy-$RWD_ENV" $HOME/.ssh/authorized_keys
  # Erwartet: genau die Zeile aus 3.3

  ---------------------------------------------------
  3.5 Host-Schluessel des Servers fuer GitLab (DEPLOY_KNOWN_HOSTS)
  ---------------------------------------------------

  Der Job prueft, dass er wirklich mit diesem Server spricht. Dafuer
  braucht GitLab den Host-Schluessel - als Zeile "<Servername> <Schluessel>".
  Der Servername muss GENAU der sein, der in DEPLOY_HOST (5.3) steht.

  export DEPLOY_HOST=<Servername, wie der Runner ihn anspricht>

  HOSTKEY=$(cut -d' ' -f1,2 /etc/ssh/ssh_host_ed25519_key.pub)

  printf '%s %s\n' "$DEPLOY_HOST" "$HOSTKEY" > $RWD_HOME/keys/known_hosts_zeile.txt

  cat $RWD_HOME/keys/known_hosts_zeile.txt
  # Erwartet: <Servername> ssh-ed25519 AAAA...
  # Gegenprobe (optional, auf dem Runner-Host):
  #   ssh-keyscan -t ed25519 <Servername>
  # muss denselben Schluessel zeigen.

  ---------------------------------------------------
  3.6 Werte fuer GitLab bereitlegen
  ---------------------------------------------------

  Fuer SCHRITT 5.3 werden diese zwei Texte gebraucht (anzeigen, markieren,
  in das GitLab-Feld kopieren - nicht in Mail oder Ticket):

  cat $RWD_HOME/keys/gitlab-deploy-$RWD_ENV
  # Erwartet: mehrere Zeilen; die erste beginnt mit fuenf Bindestrichen
  #           und "BEGIN OPENSSH ...", die letzte mit "END OPENSSH ...".
  # -> Wert fuer DEPLOY_SSH_KEY (alle Zeilen, auch die erste und die letzte)

  cat $RWD_HOME/keys/known_hosts_zeile.txt
  # -> Wert fuer DEPLOY_KNOWN_HOSTS

  Die Dateien bleiben liegen, bis SCHRITT 5.3 erledigt ist. Danach 3.7.

  ---------------------------------------------------
  3.7 Privaten Schluessel loeschen  (NACH SCHRITT 5.3)
  ---------------------------------------------------

  ls $RWD_HOME/keys
  # Erwartet: authorized_keys_zeile.txt  gitlab-deploy-dev
  #           gitlab-deploy-dev.pub      known_hosts_zeile.txt

  rm $RWD_HOME/keys/gitlab-deploy-$RWD_ENV

  ls $RWD_HOME/keys
  # Erwartet: der private Schluessel (ohne .pub) ist weg.
  # Ging er verloren, bevor er in GitLab war: 3.2 bis 3.6 neu.

  ---------------------------------------------------
  5.3 CI/CD-Variablen anlegen  (je Umgebung)
  ---------------------------------------------------

  # Settings > CI/CD > Variables > Add variable - fuer JEDE Zeile unten
  # eine Variable. Bei allen:
  #   Protect variable: AN
  #   Environment scope: development (fuer DEV) bzw. production (fuer PROD)
  #     (den Namen eintippen, falls er nicht in der Liste steht)
  #
  #   Key                 Type      Wert
  #   ------------------  --------  ----------------------------------------
  #   DEPLOY_HOST         Variable  Servername (genau wie in 3.5)
  #   DEPLOY_USER         Variable  oracle
  #   DEPLOY_SSH_KEY      File      privater Schluessel aus 3.6, alle Zeilen
  #                                 inkl. erster/letzter Zeile, am Ende eine
  #                                 Leerzeile
  #   DEPLOY_KNOWN_HOSTS  Variable  Zeile aus 3.5 (known_hosts_zeile.txt)
  #   DEPLOY_WAIT         Variable  300  (optional: Sekunden Wartezeit)
  #
  # Also 4 bis 5 Variablen mit Scope "development" (Werte vom DEV-Server)
  # und dieselben 4 bis 5 mit Scope "production" (Werte vom PROD-Server).
  # DEPLOY_SSH_KEY kann nicht "masked" werden (mehrzeilig) - das ist normal,

BEKANNTE PROBLEME
==========================================================================

  Problem : Job deploy_dev / deploy_prod bleibt "pending", startet nie.
  Ursache : Kein Runner mit dem Tag reports-deploy online.
  Loesung : SCHRITT 4.

  Problem : Job rot: "DEPLOY_HOST: DEPLOY_HOST not set"
  Ursache : Variablen fehlen fuer diese Umgebung, oder Branch/Tag nicht
            geschuetzt (geschuetzte Variablen gibt es nur dort).
  Loesung : 5.1 / 5.2 (Schutz) und 5.3 (Scope development / production).

  Problem : Job rot: "Host key verification failed."
  Ursache : DEPLOY_KNOWN_HOSTS passt nicht zum Server oder der Name darin
            ist ein anderer als in DEPLOY_HOST.
  Loesung : 3.5 mit genau dem Namen aus DEPLOY_HOST wiederholen, 5.3.

  Problem : Job rot: "Permission denied (publickey)."
  Ursache : falscher privater Schluessel in GitLab, Zeile fehlt in
            authorized_keys, oder from="..." ist nicht die IP, mit der der
            Runner beim Server ankommt (NAT, Proxy).
  Loesung : 3.4 pruefen; auf dem Server  grep sshd /var/log/secure | tail
            (als root) zeigt die wirkliche Absender-IP -> in from= eintragen.

  Problem : Job rot: "ERROR: unknown command ..." oder "usage: ..."
  Ursache : command= in authorized_keys zeigt auf ein anderes Skript, oder
            ci_deploy.sh und rwdeploy.sh passen nicht zusammen.
  Loesung : 3.3 / 3.4; beide Dateien aus demselben Stand nehmen.

  Problem : Job rot: "ERROR: path not allowed: Reports/source/..." oder
            "path not allowed: source/..."
  Ursache : alte rwdeploy.sh (Aufbau Reports/...) auf dem Server, oder
            alte ci_deploy.sh im Repository.
  Loesung : 1.1 (Version pruefen) und SCHRITT 6 (ci_deploy.sh ersetzen).

  Problem : deploy_prod rot: "the tagged commit holds no report (.rdf) or
            image - nothing to deploy, check the tag"
  Ursache : Tag auf einem Check-in ohne Bericht (z.B. nur Skripte).
  Loesung : Tag loeschen (ROLLBACK), mit release_tag.ps1 den Check-in des
            Berichts taggen.

  Problem : deploy_prod rot: "the tag is on a merge commit"
  Ursache : Zwei Kollegen haben gleichzeitig eingecheckt, der Tag sitzt auf
            dem Zusammenfuehrungs-Check-in.
  Loesung : Tag loeschen, mit release_tag.ps1 den Check-in des Berichts
            taggen.

  Problem : Job endet mit "deploy still pending after 300s"
  Ursache : Kopierer laeuft nicht oder ist beschaeftigt.
  Loesung : auf dem Server  $RWD_BIN/rwdeploy.sh list  und
            ls $RWD_HOME/incoming ; dann  $RWD_BIN/rwdeploy.sh work  von
            Hand starten; cron (1.6) pruefen.

  Problem : DEV meldet "WARNING: last deploy ... is not an ancestor"
  Ursache : Die Historie von main wurde umgeschrieben (force push).
  Loesung : Nur die Dateien dieses Check-ins wurden verteilt. DEV pruefen,
            ggf. Startpunkt neu setzen (1.7). Force push auf main
            verbieten (5.1).

  Problem : Im Menue steht ein Eintrag rot "(Skript fehlt)".
  Ursache : Das Skript liegt nicht im Ordner deploy\ des Clones.
  Loesung : git pull (pull.ps1); SkriptPfad in menu.ini pruefen.
