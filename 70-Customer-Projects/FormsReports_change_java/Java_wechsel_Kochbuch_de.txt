==============================================================================
  Kochbuch: Neues Oracle JDK fuer Forms & Reports (FMW 12.2.1.4 / 14.1.2)
            installieren, versionsneutralen Link anlegen, Domain umstellen
==============================================================================
  Zielgruppe : Administrator der Forms-/Reports-Umgebung (Linux, bash, vi)
  Umgebung   : Oracle Linux 8 / 9, Oracle FMW Forms & Reports mit WebLogic,
               Server-JDK = Oracle JDK (12.2.1.4: JDK 8, 14.1.2: JDK 21)
  Erstellt   : 2026-11-17, getestet auf dem 14.1.2-Testsystem (JDK 21)
  Grundlage  : IHateWeblogic/07-Maintenance/domain_jdk_path.sh
                 (dieselbe Umstellung automatisch, --apply)
               IHateWeblogic/70-Customer-Projects/tools/bash/java_check_fmw.sh
                 (Kunden-Tool, nur lesend: Gesamtbild vorher / nachher,
                 Windows: tools/powershell/java_check_fmw.ps1)
               IHateWeblogic/09-Install/docs/08-oracle_setup_domain.md 3b
               IHateWeblogic/09-Install/docs/01-root_setup_java.md
               JDK 21 fuer FMW: MOS-Patch 35702194 (Oracle JDK 21)
  Wichtig    : - Der Installer und WLST (createDomain, updateDomain, Config
                 Wizard) loesen einen Link auf und schreiben das ECHTE
                 Verzeichnis (jdk-21.0.12.1) in die Dateien. Ein spaeteres
                 Umbiegen des Links kommt dort dann nicht an.
               - Nach dieser Umstellung ist ein JDK-Update nur noch:
                 neues JDK auspacken (STEP 2), Einstellungen uebernehmen
                 (STEP 3), Link umbiegen (STEP 5), neu starten.
               - Das zweite JDK im Home ($ORACLE_HOME/oracle_common/jdk)
                 ist kein Link und wird NICHT angefasst.

ZIELZUSTAND
------------------------------------------------------------------------------
  Komponente                         Ziel                            Schritt
  JDK-Verzeichnis                    /oracle/java/jdk-21.0.x         STEP 2
  java.security / cacerts            wie im alten JDK                STEP 3
  Link                               /oracle/java/jdk-21 -> jdk-...  STEP 5
  Domain, oui/, bin/                 JAVA_HOME = Link                STEP 6
  laufende Server / Node Manager     .../jdk-21/bin/java             STEP 7

VORAUSSETZUNGEN
------------------------------------------------------------------------------
  - Wartungsfenster: fuer STEP 5 bis 7 wird die Umgebung gestoppt.
  - VM-Snapshot oder Datensicherung durch das zustaendige Team.
  - Das neue JDK als tar.gz (Linux x64), aus MOS-Patch 35702194 (JDK 21)
    oder dem passenden JDK-8-Patch fuer 12.2.1.4.
  - Platz: ca. 350 MB je JDK, das alte JDK bleibt stehen.

  Was wo landet (Beispielpfade - in STEP 0 an das System anpassen):

    /oracle/java/                        $JAVA_BASE
      jdk-21.0.12.1/                     altes JDK (bleibt fuer den Rueckweg)
      jdk-21.0.13.1/                     $NEWJDK  <- STEP 2 (aus dem tar.gz)
      jdk-21  -> jdk-21.0.13.1           $JDK_LINK  <- STEP 5
    /oracle/install/jdk_wechsel/         $WORK  <- STEP 0
      jdk-21.0.13.1_linux-x64_bin.tar.gz     von MOS, hierher kopiert
      logs/                              $LOGDIR (Ausgaben aller Schritte,
                                         alter Pfad, alter Link-Stand)
      backup/                            $BACKUP  <- STEP 6 (tar der Dateien)

  Regeln fuer den ganzen Lauf:
  - Jeder Befehl einzeln, nach jedem Befehl die Ausgabe mit "Erwartet"
    vergleichen.
  - Nichts loeschen: das alte JDK bleibt, bis der naechste Wechsel laeuft.

==============================================================================
STEP 0: Variablen setzen und pruefen  (in JEDEM neuen Terminal, als oracle)
==============================================================================

  export ORACLE_HOME=/oracle/product/fmw

  export DOMAIN_HOME=/oracle/user_projects/domains/fr_domain

  export JAVA_BASE=/oracle/java

  export JDK_LINK=$JAVA_BASE/jdk-21

  export WORK=/oracle/install/jdk_wechsel

  export LOGDIR=$WORK/logs

  export BACKUP=$WORK/backup

  # JDK 8 (12.2.1.4): JDK_LINK=$JAVA_BASE/jdk-8 - sonst alles gleich.

  export TOOLS=/oracle/tools
  # Verzeichnis der IHateWeblogic-Kunden-Tools (Start_beim_Kunden_kochbuch,
  # SCHRITT 1). Keine Tools auf dem Host? -> 1.0 und 7.1 auslassen.

  echo "ORACLE_HOME=$ORACLE_HOME DOMAIN_HOME=$DOMAIN_HOME"

  echo "JAVA_BASE=$JAVA_BASE JDK_LINK=$JDK_LINK WORK=$WORK"
  # Ein Wert LEER? -> die export-Zeilen oben noch einmal.

  ls -d $ORACLE_HOME/oui $DOMAIN_HOME/config
  # Erwartet: beide Verzeichnisse werden angezeigt.
  # "No such file" -> Pfad in den export-Zeilen korrigieren.

  mkdir -p $LOGDIR $BACKUP

==============================================================================
STEP 1: Ist-Stand  (als oracle, System darf laufen)
==============================================================================

  ---------------------------------------------------
  1.0 Gesamtbild mit dem Tool (wenn vorhanden)
  ---------------------------------------------------

  $TOOLS/java_check_fmw.sh -t $LOGDIR
  # Zeigt in einem Lauf: JAVA_HOME aller Konfigurationsdateien (Link oder
  # Versionsverzeichnis), das mitgelieferte JDK oracle_common/jdk, das Java
  # von Reports, die laufenden Prozesse und jede Datei mit einem JDK-Pfad.
  # Erwartet vor der Umstellung: WARN "versioned directory, not the link"
  # fuer die Dateien, die STEP 6 aendert. FAIL bei oracle_common/jdk ->
  # ZUERST "Bekannte Probleme" (Reports startet nicht mehr) lesen.

  ---------------------------------------------------
  1.1 Welches JDK steht in den Dateien?
  ---------------------------------------------------

  grep -n '^JAVA_HOME=' $ORACLE_HOME/oui/.globalEnv.properties
  # Erwartet z.B.: 3:JAVA_HOME=/oracle/java/jdk-21.0.12.1

  ALT=$(sed -n 's/^JAVA_HOME=//p' $ORACLE_HOME/oui/.globalEnv.properties)

  echo "ALT=$ALT"
  # Das ist der alte, harte Pfad, der in STEP 6 ersetzt wird.

  echo "$ALT" > $LOGDIR/01_alter_pfad.txt
  # In einem neuen Terminal: ALT=$(cat $LOGDIR/01_alter_pfad.txt)

  # Entscheidung:
  #   ALT = $JDK_LINK (z.B. /oracle/java/jdk-21)
  #       -> Umgebung steht schon auf dem Link: nur STEP 2, 3, 4, 5, 7.
  #   ALT = Versionsverzeichnis (jdk-21.0.12.1, /usr/java/jdk...)
  #       -> erstmalige Umstellung: alle Schritte.

  ---------------------------------------------------
  1.2 Mit welchem JDK laufen die Prozesse?
  ---------------------------------------------------

  ps -eo args | grep '[j]ava -' | awk '{print $1}' | sort | uniq -c | tee $LOGDIR/01_java_prozesse.txt
  # Erwartet z.B.:
  #   2 /oracle/product/fmw/oracle_common/jdk/bin/java    (Reports-Engines)
  #   4 /oracle/java/jdk-21.0.12.1/bin/java               (WLS, Node Manager)

  ---------------------------------------------------
  1.3 Gibt es den Link schon?
  ---------------------------------------------------

  ls -l $JAVA_BASE
  # Erwartet z.B.:
  #   jdk-21 -> /oracle/java/jdk-21.0.12.1     (Link vorhanden)
  #   jdk-21.0.12.1
  # Kein "jdk-21 ->" -> der Link wird in STEP 5 neu angelegt.

  readlink -f $JDK_LINK | tee $LOGDIR/01_link_vorher.txt
  # Erwartet: das aktuelle Ziel - oder keine Ausgabe (kein Link).

==============================================================================
STEP 2: Neues JDK auspacken  (als Eigentuemer von $JAVA_BASE, oft root;
        System darf laufen)
==============================================================================

  # Als root: zuerst STEP 0 in diesem Terminal wiederholen.

  ls -l $WORK/jdk-*_linux-x64_bin.tar.gz
  # Erwartet: genau EINE Datei, z.B. jdk-21.0.13.1_linux-x64_bin.tar.gz

  TGZ=$(ls $WORK/jdk-*_linux-x64_bin.tar.gz)

  NEWJDK=$JAVA_BASE/$(tar -tzf "$TGZ" | head -1 | cut -d/ -f1)

  echo "NEWJDK=$NEWJDK"
  # Erwartet z.B.: NEWJDK=/oracle/java/jdk-21.0.13.1

  echo "$NEWJDK" > $LOGDIR/02_neues_jdk.txt

  ls -d $NEWJDK
  # Erwartet: "No such file or directory" (noch nicht ausgepackt).
  # Verzeichnis gibt es schon? -> nicht noch einmal auspacken, weiter mit 2.x.

  tar -xzf "$TGZ" -C $JAVA_BASE

  $NEWJDK/bin/java -version
  # Erwartet z.B.: java version "21.0.13.1" 2026-11-17 LTS

  ls -ld $NEWJDK
  # Erwartet: lesbar fuer oracle (drwxr-xr-x).

==============================================================================
STEP 3: Einstellungen aus dem alten JDK uebernehmen  (wie STEP 2)
==============================================================================

  # java.security und cacerts liegen IM JDK-Verzeichnis. Das neue JDK
  # bringt die Oracle-Standardwerte mit - eigene Aenderungen fehlen dort.

  NEWJDK=$(cat $LOGDIR/02_neues_jdk.txt)

  ALT=$(cat $LOGDIR/01_alter_pfad.txt)

  OLDJDK=$(readlink -f $ALT)

  echo "OLDJDK=$OLDJDK NEWJDK=$NEWJDK"

  ---------------------------------------------------
  3.1 SecureRandom (schneller Start von WebLogic)
  ---------------------------------------------------

  SEC=conf/security/java.security
  # JDK 8 (12.2.1.4): SEC=jre/lib/security/java.security

  echo "SEC=$SEC"

  grep -n '^securerandom.source=' $OLDJDK/$SEC
  # Erwartet: 156:securerandom.source=file:/dev/./urandom
  # (JDK 8: andere Zeilennummer, gleicher Text)

  grep -n '^securerandom.source=' $NEWJDK/$SEC
  # file:/dev/./urandom  -> schon gesetzt (z.B. durch 02b-root_os_java.sh),
  #                         nichts zu tun, weiter mit 3.2
  # file:/dev/random     -> Oracle-Standard eines frisch ausgepackten JDK,
  #                         die naechsten Befehle ausfuehren

  cp -p $NEWJDK/$SEC $NEWJDK/$SEC.orig

  vi $NEWJDK/$SEC
  # Zeile securerandom.source=file:/dev/random aendern in:

securerandom.source=file:/dev/./urandom

  grep -n '^securerandom.source=' $NEWJDK/$SEC
  # Erwartet: 156:securerandom.source=file:/dev/./urandom

  ---------------------------------------------------
  3.2 Eigene CA-Zertifikate in cacerts?
  ---------------------------------------------------

  $OLDJDK/bin/keytool -list -cacerts -storepass changeit | grep trustedCertEntry | cut -d, -f1 | sort > $LOGDIR/03_cacerts_alt.txt

  $NEWJDK/bin/keytool -list -cacerts -storepass changeit | grep trustedCertEntry | cut -d, -f1 | sort > $LOGDIR/03_cacerts_neu.txt

  # JDK 8 kennt "-cacerts" nicht: dort statt "-cacerts" immer
  # "-keystore $OLDJDK/jre/lib/security/cacerts" bzw.
  # "-keystore $NEWJDK/jre/lib/security/cacerts" schreiben.

  comm -23 $LOGDIR/03_cacerts_alt.txt $LOGDIR/03_cacerts_neu.txt
  # Erwartet: keine Ausgabe -> nichts zu tun.
  # Zeilen mit "[jdk]" (z.B. "luxtrustglobalrootca [jdk]") = Standard-CAs,
  # die Oracle im neuen JDK entfernt hat -> ignorieren (KNOWN AND HARMLESS).
  # Aliasnamen OHNE "[jdk]" (z.B. "firmen-root-ca") -> eigene CAs: je Alias
  # aus dem alten JDK exportieren und ins neue importieren:

  $OLDJDK/bin/keytool -exportcert -cacerts -storepass changeit -alias <ALIAS> -file $WORK/<ALIAS>.cer

  $NEWJDK/bin/keytool -importcert -cacerts -storepass changeit -noprompt -alias <ALIAS> -file $WORK/<ALIAS>.cer
  # Erwartet: Certificate was added to keystore
  # Anderes cacerts-Kennwort als "changeit"? -> -storepass weglassen,
  # keytool fragt dann danach.

STEP 5: Link anlegen oder umbiegen  (als Eigentuemer von $JAVA_BASE)
==============================================================================

  NEWJDK=$(cat $LOGDIR/02_neues_jdk.txt)

  ls -l $JDK_LINK
  # "No such file"            -> 5.1 (erstes Mal)
  # "jdk-21 -> ...jdk-21.0.x" -> 5.2 (Update)
  # Ein ECHTES Verzeichnis jdk-21 (kein "->")? -> STOP, erst umbenennen.

  ---------------------------------------------------
  5.1 Erstes Mal: Link anlegen
  ---------------------------------------------------

  ln -s $NEWJDK $JDK_LINK

  ---------------------------------------------------
  5.2 Update: Link umbiegen
  ---------------------------------------------------

  ln -sfn $NEWJDK $JDK_LINK

  ---------------------------------------------------
  5.3 Kontrolle
  ---------------------------------------------------

  ls -l $JDK_LINK
  # Erwartet: jdk-21 -> /oracle/java/jdk-21.0.13.1

  $JDK_LINK/bin/java -version
  # Erwartet: java version "21.0.13.1" ...

  # Erwartet (14.1.2-Testsystem, 23 Dateien):
  #   $DOMAIN_HOME/bin/setDomainEnv.sh
  #   $DOMAIN_HOME/bin/setNMJavaHome.sh
  #   $DOMAIN_HOME/nodemanager/nodemanager.properties

  #     frmbld.sh frmcmp.sh frmcmp_batch.sh frmf2xlf.sh frmf2xml.sh
  #     frmplsqlconv.sh frmxlf2f.sh frmxml2f.sh frmxmlsg.sh frmxmlv.sh
  #   $DOMAIN_HOME/init-info/domain-info.xml nodemanager-properties.xml
  #     startscript.xml tokenValue.properties
  #   $ORACLE_HOME/oui/.globalEnv.properties
  #   $ORACLE_HOME/oui/bin/compareInventory.sh launch.sh setProperty.sh
  #     viewInventory.sh
  #   $ORACLE_HOME/bin/aqxmlctl
  # Reports-only-Domain: ohne die FORMS-Zeilen. 12.2.1.4: aehnlich.
  # NICHT aendern: Logs, *.bak, servers/*/adr (Incidents),
  # $ORACLE_HOME/inventory (Historie) - die stehen bewusst nicht in der Liste.

  ---------------------------------------------------
  6.2 Sicherung der Dateien
  ---------------------------------------------------

  tar -czf $BACKUP/06_jdk_dateien_vorher.tar.gz -T $LOGDIR/06_dateien.txt 2>&1 | tee $LOGDIR/06_tar.txt
  # Erwartet: "tar: Removing leading `/' from member names" (harmlos),
  #           ggf. auch "... from hard link targets" (harmlos).

  tar -tzf $BACKUP/06_jdk_dateien_vorher.tar.gz | wc -l
  # Erwartet: dieselbe Anzahl wie Zeilen in 06_dateien.txt
  #           (wc -l < $LOGDIR/06_dateien.txt)

  ---------------------------------------------------
  6.3 Dateien aendern

  # In jeder Datei der Liste den alten Pfad durch den Link ersetzen:
  #   alt:  der Wert von $ALT      (z.B. /oracle/java/jdk-21.0.12.1)
  #   neu:  der Wert von $JDK_LINK (z.B. /oracle/java/jdk-21)
  # Jede Datei einzeln, Beispiele:

  vi $DOMAIN_HOME/bin/setDomainEnv.sh

  vi $DOMAIN_HOME/bin/setNMJavaHome.sh

  vi $DOMAIN_HOME/nodemanager/nodemanager.properties

  vi $ORACLE_HOME/oui/.globalEnv.properties

  # ... und so weiter fuer alle Dateien aus 6.1.
  # Viele Dateien (Forms-Instanz, init-info)? -> ANHANG A.

  # Datei angezeigt -> dort fehlt noch eine Stelle (vi, 6.3).

BEKANNTE PROBLEME
------------------------------------------------------------------------------
  Problem : Nach updateDomain / Config Wizard / Erweiterung der Domain laeuft
            wieder das alte JDK.
  Ursache : WLST schreibt beim Speichern das aufgeloeste, echte Verzeichnis.
  Loesung : STEP 1.1 und STEP 6 wiederholen (oder domain_jdk_path.sh).

  Problem : Reports startet nach dem Wechsel nicht mehr (rwserver / Engines
            kommen nicht hoch).
  Ursache : Das mitgelieferte JDK $ORACLE_HOME/oracle_common/jdk wurde mit
            umgestellt - durch einen Link auf das neue JDK ersetzt oder
            ueberschrieben - oder reports.sh wurde von Hand auf das neue
            JDK geaendert. Reports braucht SEIN JDK (14.1.2: Oracle JDK 17).
  Loesung : $TOOLS/java_check_fmw.sh, Abschnitt 2 (oracle_common/jdk) und 3
            (reports.sh, libjvm des rwserver) zeigen es. Das Original-
            Verzeichnis zurueckholen (Sicherung / VM-Snapshot), reports.sh
            aus der Sicherung - oracle_common/jdk nie durch einen Link
            ersetzen.

  Problem : Reports-Engines laufen weiter mit oracle_common/jdk.
  Ursache : Produkteigenschaft - reports.sh / rwengine starten die Engines
            immer mit dem mitgelieferten JDK im Home.
  Loesung : keine; dieses JDK kommt mit den Oracle-Patches des Homes.

  Problem : WebLogic startet sehr langsam (Minuten bis "RUNNING").
  Ursache : SecureRandom-Einstellung fehlt im neuen JDK.
  Loesung : STEP 3.1.

  Problem : HTTPS-/LDAPS-Verbindungen aus WebLogic oder Reports schlagen
            nach dem Wechsel fehl ("PKIX path building failed").
  Ursache : eigene CA fehlt in cacerts des neuen JDK.
  Loesung : STEP 3.2.

  Problem : OPatch / wlst.sh melden "JAVA_HOME ... not found".
  Ursache : altes JDK geloescht, aber .globalEnv.properties zeigt noch dorthin.
  Loesung : STEP 6 (oui/.globalEnv.properties auf den Link).
