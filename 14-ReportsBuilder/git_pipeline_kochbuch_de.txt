SO LAEUFT ES (Ueberblick)
-------------------------

  Entwickler: checkin.ps1 --push--> GitLab main --Job deploy_dev--> DEV
  Entwickler: release_tag.ps1 --Tag prod-...--> GitLab --Job deploy_prod--> PROD
                                                  --Job notify_prod_*--> Mail

  Der Job laeuft auf dem GitLab-Runner, baut ein tar mit den Dateien und
  schickt es per SSH an rwdeploy.sh auf dem Server. rwdeploy.sh prueft das
  tar, kopiert die Dateien in die Reports-Ordner (mit Sicherung) und meldet
  das Ergebnis zurueck - die Pipeline wird gruen oder rot.

  Netz: Runner -> GitLab (HTTPS, holt die Jobs ab), Runner -> Server Port 22
  (SSH), Runner -> Mail-Relay (SCHRITT 9). Die Server rufen GitLab nie auf.

SCHRITT 3: Deploy-Schluessel  (als oracle, je Server einmal)
==========================================================================

  Jeder Server bekommt sein eigenes Schluesselpaar:
  - der oeffentliche Teil kommt in authorized_keys dieses Servers und
    darf dort NUR rwdeploy.sh starten, NUR vom Runner aus;
  - der private Teil kommt in die GitLab-Variable DEPLOY_SSH_KEY dieser
    Umgebung (SCHRITT 5.3) und wird danach auf dem Server geloescht.

  Erst fuer DEV (RWD_ENV=dev), dann fuer PROD (RWD_ENV=prod).

  ---------------------------------------------------
  3.1 Variablen pruefen
  ---------------------------------------------------

  echo "RWD_ENV=$RWD_ENV  RWD_HOME=$RWD_HOME  RUNNER_IP=$RUNNER_IP"
  # Leer? -> erst SCHRITT 0.

  ---------------------------------------------------
  3.2 Schluesselpaar erzeugen
  ---------------------------------------------------

  mkdir -p $RWD_HOME/keys

  chmod 700 $RWD_HOME/keys

  cd $RWD_HOME/keys

  ssh-keygen -t ed25519 -N '' -C gitlab-deploy-$RWD_ENV -f ./gitlab-deploy-$RWD_ENV
  # Erwartet:
  #   Generating public/private ed25519 key pair.
  #   Your identification has been saved in ./gitlab-deploy-dev
  #   Your public key has been saved in ./gitlab-deploy-dev.pub

  ls -l $RWD_HOME/keys
  # Erwartet: gitlab-deploy-dev (privat) und gitlab-deploy-dev.pub

  ---------------------------------------------------
  3.3 Zeile fuer authorized_keys vorbereiten
  ---------------------------------------------------

  PUBKEY=$(cat $RWD_HOME/keys/gitlab-deploy-$RWD_ENV.pub)

  echo "$PUBKEY"
  # Erwartet: ssh-ed25519 AAAA... gitlab-deploy-dev

  printf 'command="%s",restrict,from="%s" %s\n' "$RWD_BIN/rwdeploy.sh" "$RUNNER_IP" "$PUBKEY" > $RWD_HOME/keys/authorized_keys_zeile.txt

  cat $RWD_HOME/keys/authorized_keys_zeile.txt
  # Erwartet (EINE Zeile):
  #   command="/u01/app/oracle/rwdeploy/bin/rwdeploy.sh",restrict,from="<runner-ip>" ssh-ed25519 AAAA... gitlab-deploy-dev
  # Bedeutung:
  #   command=  jede Anmeldung mit diesem Schluessel startet nur rwdeploy.sh
  #   restrict  keine Shell, keine Weiterleitungen
  #   from=     nur vom Runner (IP aus V.2)

  ---------------------------------------------------
  3.4 Zeile in authorized_keys eintragen
  ---------------------------------------------------

  mkdir -p $HOME/.ssh

  chmod 700 $HOME/.ssh

  grep -c "gitlab-deploy-$RWD_ENV" $HOME/.ssh/authorized_keys
  # 0 oder "No such file"   -> weiter mit dem naechsten Befehl
  # 1                       -> alte Zeile vorhanden: in vi zuerst diese
  #                            Zeile loeschen ( dd ), dann wie unten

  vi $HOME/.ssh/authorized_keys

  # In vi:  G  (ans Dateiende), dann
  #   :r /u01/app/oracle/rwdeploy/keys/authorized_keys_zeile.txt
  # (fuegt die vorbereitete Zeile ein - nichts von Hand tippen)
  # Dann  Esc  und  :wq .

  chmod 600 $HOME/.ssh/authorized_keys

  grep "gitlab-deploy-$RWD_ENV" $HOME/.ssh/authorized_keys
  # Erwartet: genau die Zeile aus 3.3

  ---------------------------------------------------
  3.5 Host-Schluessel des Servers fuer GitLab (DEPLOY_KNOWN_HOSTS)
  ---------------------------------------------------

  Der Job prueft, dass er wirklich mit diesem Server spricht. Dafuer
  braucht GitLab den Host-Schluessel - als Zeile "<Servername> <Schluessel>".
  Der Servername muss GENAU der sein, der in DEPLOY_HOST (5.3) steht.

  export DEPLOY_HOST=<Servername, wie der Runner ihn anspricht>

  HOSTKEY=$(cut -d' ' -f1,2 /etc/ssh/ssh_host_ed25519_key.pub)

  printf '%s %s\n' "$DEPLOY_HOST" "$HOSTKEY" > $RWD_HOME/keys/known_hosts_zeile.txt

  cat $RWD_HOME/keys/known_hosts_zeile.txt
  # Erwartet: <Servername> ssh-ed25519 AAAA...
  # Gegenprobe (optional, auf dem Runner-Host):
  #   ssh-keyscan -t ed25519 <Servername>
  # muss denselben Schluessel zeigen.

  ---------------------------------------------------
  3.6 Werte fuer GitLab bereitlegen
  ---------------------------------------------------

  Fuer SCHRITT 5.3 werden diese zwei Texte gebraucht (anzeigen, markieren,
  in das GitLab-Feld kopieren - nicht in Mail oder Ticket):

  cat $RWD_HOME/keys/gitlab-deploy-$RWD_ENV
  # Erwartet: mehrere Zeilen; die erste beginnt mit fuenf Bindestrichen
  #           und "BEGIN OPENSSH ...", die letzte mit "END OPENSSH ...".
  # -> Wert fuer DEPLOY_SSH_KEY (alle Zeilen, auch die erste und die letzte)

  cat $RWD_HOME/keys/known_hosts_zeile.txt
  # -> Wert fuer DEPLOY_KNOWN_HOSTS

  Die Dateien bleiben liegen, bis SCHRITT 5.3 erledigt ist. Danach 3.7.

  ---------------------------------------------------
  3.7 Privaten Schluessel loeschen  (NACH SCHRITT 5.3)
  ---------------------------------------------------

  ls $RWD_HOME/keys
  # Erwartet: authorized_keys_zeile.txt  gitlab-deploy-dev
  #           gitlab-deploy-dev.pub      known_hosts_zeile.txt

  rm $RWD_HOME/keys/gitlab-deploy-$RWD_ENV

  ls $RWD_HOME/keys
  # Erwartet: der private Schluessel (ohne .pub) ist weg.
  # Ging er verloren, bevor er in GitLab war: 3.2 bis 3.6 neu.


==========================================================================
SCHRITT 4: Projekt-Runner einrichten  (GitLab-Admin, root auf dem Runner-Host)
==========================================================================

  Die Jobs laufen nur auf einem Runner mit dem Tag  reports-deploy
  (steht so in .gitlab-ci.yml). Wir richten dafuer einen eigenen
  PROJEKT-RUNNER ein: nur fuer das Projekt oracle-report, nur fuer
  geschuetzte Branches/Tags (main, prod-*), Executor "shell".

  Der Runner holt sich seine Jobs selbst bei GitLab ab (ausgehend HTTPS) -
  eingehend ist auf dem Runner-Host nichts noetig. Zu den Reports-Servern
  geht er ausgehend auf Port 22.

  Teile, die nur mit dem echten GitLab gehen (Menue-Namen, Ausgabe von
  "register"), sind nach der GitLab-Doku geschrieben; beim Kunden am
  2026-11-13 so durchgefuehrt (mit der Erfahrung "Runner zu alt", 4.3):
    https://docs.gitlab.com/ci/runners/runners_scope/#project-runners
    https://docs.gitlab.com/runner/install/linux-repository/
    https://docs.gitlab.com/runner/register/
    https://docs.gitlab.com/runner/executors/shell/

  ---------------------------------------------------
  4.1 Gibt es den Runner schon?
  ---------------------------------------------------

  # Browser: Projekt oracle-report > Settings > CI/CD > Runners
  # Ein Projekt-Runner mit dem Tag "reports-deploy", Status gruen (online)?
  #   ja   -> weiter mit 4.7 (pruefen) - KEINEN zweiten anlegen: zwei Runner
  #           mit diesem Tag nehmen beide Jobs an
  #   nein -> 4.2
  #
  # Den Tag reports-deploy hat NUR der Deploy-Runner. Andere Runner (auch
  # Instanz-Runner) ohne diesen Tag nehmen unsere Jobs nicht.
  #
  # Ein schon vorhandener Runner wird durch die folgenden Schritte NICHT
  # ueberschrieben: "register" haengt in /etc/gitlab-runner/config.toml
  # einen weiteren [[runners]]-Block an, ein gitlab-runner-Dienst bedient
  # beliebig viele Runner.

  ---------------------------------------------------
  4.2 Runner-Host festlegen
  ---------------------------------------------------

  Eine Linux-VM (z.B. Oracle Linux 9), die
  - GitLab per HTTPS erreicht (ausgehend, Port 443),
  - DEV und PROD auf Port 22 erreicht (ausgehend),
  - KEIN Reports-Server ist (der Runner gehoert nicht auf die Zielserver).

  SICHERHEIT bei einem Host, auf dem schon Runner anderer Projekte laufen:
  Beim Shell-Executor laufen ALLE Jobs aller Runner dieses Hosts als
  derselbe Benutzer gitlab-runner. Waehrend unseres Jobs liegt der private
  Deploy-Schluessel (DEPLOY_SSH_KEY, Typ File) als Datei im Build-Ordner -
  ein gleichzeitig laufender Job eines anderen Projekts koennte ihn lesen.
  Fuer den PROD-Schluessel daher: EIGENER Host nur fuer diesen Runner.
  Mindestens: dort laeuft kein Projekt, dessen Pipeline beliebige
  Entwickler aendern koennen.

  # Auf dem Runner-Host (als root):

  hostname -f
  # Erwartet: der Name des Runner-Hosts - notieren

  ip -4 -brief addr
  # Erwartet: die IP(s) des Hosts. Die IP, mit der er bei DEV/PROD
  # ankommt, gehoert in from="..." (SCHRITT 3.3, RUNNER_IP). Hinter NAT /
  # Proxy kann es eine andere sein - Gegenprobe in 4.7.

  curl -sS -o /dev/null -w '%{http_code}\n' https://<gitlab-server>/users/sign_in
  # Erwartet: 200 (GitLab erreichbar)
  # Fehler / Zeitablauf -> Firewall / Proxy: STOP, Freigabe beantragen.

  ---------------------------------------------------
  4.3 gitlab-runner installieren  (als root auf dem Runner-Host)
  ---------------------------------------------------

  rpm -q gitlab-runner
  # "package gitlab-runner is not installed" -> weiter mit dem naechsten Befehl
  # eine Version wird angezeigt                -> schon installiert: diese
  #   Installation nutzen, NICHT neu installieren - aber VERSION pruefen:

  gitlab-runner --version
  # Erwartet: "Version: <major.minor>..." = die Version des GitLab-Servers
  # (GitLab: Hilfe-Menue "?" > "Help" oder Admin-Bereich zeigt sie).
  # GitLab-Doku: "the GitLab Runner major.minor version should stay in sync
  # with the GitLab major and minor version."
  # Gleich (oder hoeher) -> weiter mit "gitlab-runner list".
  # Deutlich aelter -> erst "Runner zu alt" (unten), sonst nimmt er die
  # Jobs nicht an (beim Kunden 2026-11-13 so passiert).

  # --- Runner zu alt: aktualisieren (NUR wenn die Version zu alt ist) ---
  #
  # Erfahrung beim Kunden 2026-11-13: alter Runner nahm keine Jobs. Geloest
  # in dieser Reihenfolge: Version geprueft -> GitLab-Runner-Repository
  # eingebunden -> Software aktualisiert -> Reboot -> den ALTEN Runner in
  # GitLab geloescht (er wurde auch nach dem Reboot noch mit der alten
  # Version angezeigt - das ist der alte Eintrag, nicht der Dienst) ->
  # Runner NEU angelegt (4.4) und mit einem NEUEN Namen registriert (4.5)
  # -> Test-Commit -> Job lief.

  curl -sS -o /root/gitlab-runner-repo.sh https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.rpm.sh

  head -20 /root/gitlab-runner-repo.sh
  # Erwartet: Skript von packages.gitlab.com - erst ansehen, dann ausfuehren

  bash /root/gitlab-runner-repo.sh
  # Erwartet: "The repository is setup! You can now install packages."

  dnf upgrade -y gitlab-runner
  # Erwartet: "Complete!" (laufende Jobs vorher abwarten - das Update
  # startet den Dienst neu)

  gitlab-runner --version
  # Erwartet: die neue Version (passend zum GitLab-Server)

  rm /root/gitlab-runner-repo.sh

  # Reboot des Runner-Hosts (beim Kunden so gemacht; mindestens
  #   systemctl restart gitlab-runner )

  # Danach: alten Runner in GitLab loeschen (Settings > CI/CD > Runners >
  # alter Runner > Loeschen) und den verwaisten Eintrag entfernen
  # ("Altlasten bereinigen" unten: verify / verify --delete). Dann 4.4.
  # --- Ende Runner zu alt ---

  # vorhandene Runner zeigen:

  gitlab-runner list
  # Erwartet: keine Zeile (neuer Host) - oder die schon vorhandenen Runner
  # (andere Projekte).

  # ALTLASTEN pruefen - bevor ein neuer Runner dazukommt. Ein Eintrag in
  # config.toml, dessen Runner in GitLab schon geloescht ist (alter
  # Versuch, abgebrochene Registrierung), fragt GitLab weiter alle paar
  # Sekunden an und fuellt das Protokoll mit Fehlern - die ueberdecken
  # spaeter die Meldungen des neuen Runners:

  gitlab-runner verify
  # Erwartet je vorhandenem Runner: "Verifying runner... is alive   runner=<id>"
  # "is removed" / "is not valid" / 403 Forbidden -> Altlast: dieser
  # Runner existiert in GitLab nicht mehr.
  # Keine Altlast -> weiter mit "journalctl" unten.
  # Altlast -> erst die folgenden Befehle (Altlasten bereinigen).

  # --- Altlasten bereinigen (NUR wenn verify oben eine Altlast zeigt) ---
  #
  # "gitlab-runner verify --delete" fragt GitLab fuer jeden Eintrag in
  # config.toml und entfernt NUR die, die GitLab nicht mehr kennt. Laufende
  # Runner bleiben. Nicht rueckgaengig zu machen - daher erst sichern. Gehoert
  # der verwaiste Eintrag zu einem anderen Projekt: vorher mit dessen
  # Verantwortlichen klaeren.
  # Doku: https://docs.gitlab.com/runner/commands/#gitlab-runner-verify

  cp -p /etc/gitlab-runner/config.toml /etc/gitlab-runner/config.toml.bak_vor_verify

  ls -l /etc/gitlab-runner/config.toml.bak_vor_verify
  # Erwartet: die Sicherung, gleiche Groesse wie config.toml

  grep -c '^\[\[runners\]\]' /etc/gitlab-runner/config.toml
  # Erwartet: Anzahl der Eintraege vorher, z.B. 3 - notieren

  gitlab-runner verify --delete
  # Erwartet: fuer die gesunden Runner "is alive", fuer die Altlast
  # "is removed" - und die Altlast wird aus config.toml geloescht.

  grep -c '^\[\[runners\]\]' /etc/gitlab-runner/config.toml
  # Erwartet: Anzahl vorher minus Zahl der Altlasten, z.B. 2

  gitlab-runner verify
  # Erwartet: nur noch "is alive". Steht noch "is removed" da -> STOP,
  # Ausgabe sichern, mit dem GitLab-Administrator klaeren.

  # Ein falscher Eintrag geloescht? Zurueck:
  #   cp -p /etc/gitlab-runner/config.toml.bak_vor_verify /etc/gitlab-runner/config.toml
  # (der Dienst liest die Datei selbst neu)

  # --- Ende Altlasten ---

  journalctl -u gitlab-runner --since "-1h" --no-pager | grep -ci error
  # Erwartet: 0 (kein Fehler in der letzten Stunde) - die saubere
  # Ausgangslage. Eine Zahl > 0: die Zeilen ansehen
  #   journalctl -u gitlab-runner --since "-1h" --no-pager | grep -i error | tail -5
  # und klaeren, bevor der neue Runner dazukommt.

  # Dann:
  #   - Sicherheit (4.2) beachten,
  #   - "concurrent" (gilt fuer ALLE Runner des Hosts zusammen) ansehen:

  grep -n '^concurrent' /etc/gitlab-runner/config.toml
  # Erwartet z.B.: concurrent = 1
  # 1 = immer nur EIN Job auf dem Host: unser Deploy wartet hinter langen
  # Jobs anderer Projekte. Bei Bedarf in vi auf 2 oder 4 setzen (der Dienst
  # liest die Datei selbst neu).
  # Danach weiter mit 4.4.

  curl -sS -o /root/gitlab-runner-repo.sh https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.rpm.sh

  head -20 /root/gitlab-runner-repo.sh
  # Erwartet: ein Shell-Skript von packages.gitlab.com (richtet das
  # dnf-Repository "runner_gitlab-runner" ein). Erst ansehen, dann ausfuehren.

  bash /root/gitlab-runner-repo.sh
  # Erwartet am Ende: "The repository is setup! You can now install packages."

  dnf install -y gitlab-runner
  # Erwartet: "Complete!" - legt den Benutzer gitlab-runner und den Dienst an

  gitlab-runner --version
  # Erwartet: Version: 17.x oder neuer

  systemctl is-active gitlab-runner
  # Erwartet: active

  rm /root/gitlab-runner-repo.sh

  ---------------------------------------------------
  4.5 Runner registrieren  (als root auf dem Runner-Host)
  ---------------------------------------------------

  # Vorher sichern und den Stand merken - register haengt nur an, aber so
  # ist der Vergleich eindeutig (bei einem neuen Host gibt es die Datei
  # evtl. noch nicht - dann "No such file", weiter):

  cp -p /etc/gitlab-runner/config.toml /etc/gitlab-runner/config.toml.bak_$(date +%Y%m%d_%H%M)

  gitlab-runner list 2>&1 | tee /root/runner_list_vorher.txt
  # Erwartet: die schon vorhandenen Runner (oder keine Zeile)

  export GITLAB_URL=https://<gitlab-server>/

  echo "GITLAB_URL=$GITLAB_URL"
  # Erwartet: die Adresse von GitLab mit / am Ende

  read -s -p "Runner-Token (glrt-...): " RUNNER_TOKEN

  echo

  echo "Token-Laenge: ${#RUNNER_TOKEN}"
  # Erwartet: eine Zahl > 20 (der Wert selbst wird nicht angezeigt).
  # 0 -> read wiederholen.

  gitlab-runner register --non-interactive --url "$GITLAB_URL" --token "$RUNNER_TOKEN" --executor shell --description "reports-deploy $(hostname -s)"
  # Erwartet am Ende: "Runner registered successfully."
  # Interaktiv ("gitlab-runner register" ohne --non-interactive) schlaegt
  # GitLab Runner als Namen den eines schon vorhandenen Runners vor - den
  # NICHT uebernehmen, einen neuen eintippen (beim Kunden 2026-11-13: der
  # vorgeschlagene alte Name wurde ersetzt durch report-deploy).
  # Tags und "Protected" wurden in 4.4 in GitLab gesetzt - beim
  # Registrieren mit glrt-Token nicht noch einmal angeben.
  # Hinweis: das Token steht dabei kurz in der Prozessliste und danach
  # in /etc/gitlab-runner/config.toml (nur root lesbar) - so sieht es die
  # GitLab-Doku vor.

  unset RUNNER_TOKEN

  # KEIN Neustart des Dienstes noetig: der laufende gitlab-runner-Dienst
  # prueft config.toml alle 3 Sekunden und laedt den neuen Eintrag selbst
  # (GitLab-Doku "Advanced configuration"). Der neue Runner ist nach
  # wenigen Sekunden aktiv - Kontrolle in 4.7.
  # "systemctl restart gitlab-runner" hier NICHT ausfuehren: ein Neustart
  # bricht laufende Jobs ALLER Runner dieses Hosts ab (auch die anderer
  # Projekte). Nur wenn der Runner nach 1-2 Minuten in 4.7 nicht "is alive"
  # / gruen ist und keine fremden Jobs laufen (Projekte fragen bzw.
  #   journalctl -u gitlab-runner --since "-5min" --no-pager | grep -i job
  # ansehen), dann:  systemctl restart gitlab-runner

  ls -l /etc/gitlab-runner/config.toml
  # Erwartet: -rw------- root root ... config.toml

  gitlab-runner list 2>&1 | tee /root/runner_list_nachher.txt

  diff /root/runner_list_vorher.txt /root/runner_list_nachher.txt
  # Erwartet: genau EINE neue Zeile ("> reports-deploy <host> ..."), die
  # alten Zeilen unveraendert. Zwei neue Zeilen = doppelt registriert ->
  # den zweiten mit  gitlab-runner unregister --name "<Name>"  entfernen
  # und in GitLab loeschen.

SCHRITT 9: Mail nach dem PROD-Deploy  (root auf dem Runner-Host, Browser)
==========================================================================

  Nach jedem PROD-Deploy (Tag prod-*) schickt die Pipeline EINE Mail:
  notify_prod_ok wenn deploy_prod gruen war, notify_prod_failed wenn er
  rot war. DEV-Pushes schicken keine Mail. Das Skript
  deploy/ci_notify_mail.sh (seit SCHRITT 6 im Repository) gibt die Mail an
  das lokale sendmail des Runner-Hosts; Postfix reicht sie an den
  Mailserver der Firma weiter.

  ALTERNATIVE (Loesung des Kunden): deploy/template_mail_in_pipe.gitlab-ci.yml
  statt template.gitlab-ci.yml - Mail nach JEDEM Deploy (DEV und PROD) an
  den Ausloeser, mit der ganzen Ausgabe von ci_deploy.sh, per curl direkt an
  den SMTP-Server (Variablen SMTP_HOST, SMTP_PORT, SMTP_MAIL_FROM, optional
  SMTP_USER / SMTP_PASS) - dann entfaellt Postfix auf dem Runner-Host und
  dieser Schritt 9. Vergleich: Git_deploy.md, Abschnitt 4 "Mail - two ways".

  Inhalt: Betreff "[PROD] <bericht>.rdf deployed - <tag>" (bzw. "FAILED"),
  Freigeber, Tag-Kommentar, Dateien des Check-ins, Links zu Pipeline und
  Job. Ein Mail-Problem macht die Freigabe NICHT rot (allow_failure) -
  der Job erscheint dann orange.

  ---------------------------------------------------
  9.1 Mailserver klaeren
  ---------------------------------------------------

  # Beim Mail-Administrator erfragen:
  #   - SMTP-Relay (Name, TLS-Port), den der Runner-Host benutzen darf
  #     Demo-Wert: mxmail01.pipperr.local, Port 587 (STARTTLS)
  #   - erlaubte Absender-Adresse (MAIL_FROM), z.B. gitlab-runner@<firma>
  #   - Empfaenger (MAIL_TO), z.B. die Verteilerliste des Reports-Teams

  export MAIL_RELAY=mxmail01.pipperr.local
  # (Demo-Wert - beim Kunden den Relay aus der Abfrage oben)

  export MAIL_PORT=587

  timeout 5 bash -c "</dev/tcp/$MAIL_RELAY/$MAIL_PORT" && echo "Relay Port $MAIL_PORT offen"
  # Erwartet: Relay Port 587 offen
  # Keine Ausgabe -> Firewall: STOP, Freigabe Runner -> Relay Port 587.

  openssl s_client -starttls smtp -connect $MAIL_RELAY:$MAIL_PORT -brief < /dev/null
  # Erwartet: "CONNECTION ESTABLISHED", "Protocol version: TLSv1.2" oder
  # "TLSv1.3", "Verification: OK"
  # "Verification error" -> die CA des Relays fehlt im System-Truststore
  # (/etc/pki/ca-trust/source/anchors/ + update-ca-trust) - siehe
  # 80-FMW-Architecture/certificates_trust_stores.md.

  ---------------------------------------------------
  9.2 Postfix als Weiterleiter einrichten  (als root)
  ---------------------------------------------------

  rpm -q postfix
  # "not installed" -> dnf install -y postfix

  postconf relayhost
  # Erwartet nach der Einrichtung: relayhost = [mxmail01.pipperr.local]:587
  # Leer ("relayhost =") -> naechster Befehl. Schon ein anderer Wert ->
  # STOP, der Host versendet schon - mit dem Mail-Administrator klaeren.

  cp -p /etc/postfix/main.cf /etc/postfix/main.cf.bak_$(date +%Y%m%d)

  postconf -e "relayhost = [$MAIL_RELAY]:$MAIL_PORT"

  postconf -e "smtp_tls_security_level = encrypt"
  # Mails zum Relay NUR verschluesselt (STARTTLS) - sonst kein Versand

  postconf -e "smtp_tls_CAfile = /etc/pki/tls/certs/ca-bundle.crt"
  # System-Truststore von Oracle Linux - prueft das Zertifikat des Relays

  postconf -e "inet_interfaces = loopback-only"
  # nimmt nur Mails vom Host selbst an - kein offener Mailserver

  postconf relayhost smtp_tls_security_level inet_interfaces
  # Erwartet:
  #   relayhost = [mxmail01.pipperr.local]:587
  #   smtp_tls_security_level = encrypt
  #   inet_interfaces = loopback-only
  # Verlangt der Relay eine Anmeldung (SASL): Benutzer / Kennwort beim
  # Mail-Administrator erfragen, smtp_sasl_auth_enable + sasl_passwd -
  # nicht Teil dieses Kochbuchs (Kennwort nie in eine Datei im Repository).

  systemctl enable --now postfix

  systemctl restart postfix

  systemctl is-active postfix
  # Erwartet: active

  ---------------------------------------------------
  9.3 Testmail vom Runner-Host  (als Benutzer gitlab-runner)
  ---------------------------------------------------

  printf 'Subject: Test Runner-Mail\n\nTest von %s\n' "$(hostname -f)" > /tmp/testmail.txt

  journalctl -u postfix --since "-5min" --no-pager | grep status=

  # "status=sent (250 ...)"
  # "status=deferred" / "bounced" -> Text dahinter dem Mail-Administrator
  # geben (meist: Absender nicht erlaubt oder Relay verweigert).

  rm /tmp/testmail.txt

  # Postfach pruefen: die Testmail ist angekommen.

BEKANNTE PROBLEME
==========================================================================

  Problem : Job deploy_dev / deploy_prod bleibt "pending", startet nie.
  Ursache : Kein Runner mit dem Tag reports-deploy online - oder der Runner
            ist "protected" und der Branch / Tag ist es nicht (SCHRITT 5.1 /
            5.2 fehlt), oder der Dienst laeuft nicht.
  Loesung : SCHRITT 4.7 (gitlab-runner verify, systemctl status
            gitlab-runner), SCHRITT 5.1 / 5.2.

  Problem : Runner ist da und gruen, nimmt aber keine Jobs an (Jobs
            bleiben "pending") - beim Kunden 2026-11-13.
  Ursache : gitlab-runner-Version zu alt fuer den GitLab-Server.
  Loesung : SCHRITT 4.3 "Runner zu alt": Repository einbinden, dnf upgrade,
            Reboot; alten Runner in GitLab loeschen (zeigt auch danach noch
            die alte Version), verify --delete; Runner neu anlegen (4.4) und
            mit NEUEM Namen registrieren (4.5); Test-Commit.

  Problem : journalctl -u gitlab-runner voll mit "403 Forbidden" /
            "is removed" / "invalid token" - auch wenn kein Job laeuft.
  Ursache : Altlast: ein Eintrag in /etc/gitlab-runner/config.toml, dessen
            Runner in GitLab geloescht ist (alter Versuch, abgebrochene
            Registrierung, Runner in der Oberflaeche entfernt).
  Loesung : SCHRITT 4.3 "Altlasten bereinigen": sichern, gitlab-runner
            verify --delete, danach nur noch "is alive".

  Problem : Deploy-Job wartet lange, bevor er startet ("pending" einige
            Minuten), DEV meldet danach evtl. "still pending".
  Ursache : Auf dem Runner-Host laufen auch Runner anderer Projekte,
            concurrent = 1 - unser Job wartet hinter deren Jobs.
  Loesung : concurrent in /etc/gitlab-runner/config.toml erhoehen (4.3) -
            besser: eigener Host fuer den Deploy-Runner (4.2).

  Problem : Jobs laufen mal hier, mal dort / zwei Runner mit dem Tag
            reports-deploy in Settings > CI/CD > Runners.
  Ursache : Doppelt registriert (4.1 uebersprungen) oder der Tag auch an
            einem anderen Runner.
  Loesung : den ueberzaehligen Runner entfernen (ROLLBACK, Projekt-Runner
            entfernen) bzw. den Tag dort loeschen.

  Problem : Job rot: "git: command not found" / "ssh: command not found"
  Ursache : Werkzeug fehlt auf dem Runner-Host (Benutzer gitlab-runner).
  Loesung : dnf install -y git openssh-clients, dann 4.7.

  Problem : Job rot: "DEPLOY_HOST: DEPLOY_HOST not set"
  Ursache : Variablen fehlen fuer diese Umgebung, oder Branch/Tag nicht
            geschuetzt (geschuetzte Variablen gibt es nur dort).
  Loesung : 5.1 / 5.2 (Schutz) und 5.3 (Scope development / production).

  Problem : Job rot: "Host key verification failed."
  Ursache : DEPLOY_KNOWN_HOSTS passt nicht zum Server oder der Name darin
            ist ein anderer als in DEPLOY_HOST.
  Loesung : 3.5 mit genau dem Namen aus DEPLOY_HOST wiederholen, 5.3.

  Problem : Job rot: "Permission denied (publickey)."
  Ursache : falscher privater Schluessel in GitLab, Zeile fehlt in
            authorized_keys, oder from="..." ist nicht die IP, mit der der
            Runner beim Server ankommt (NAT, Proxy).
  Loesung : 3.4 pruefen; auf dem Server  grep sshd /var/log/secure | tail
            (als root) zeigt die wirkliche Absender-IP -> in from= eintragen.

  Problem : Job rot: "ERROR: unknown command ..." oder "usage: ..."
  Ursache : command= in authorized_keys zeigt auf ein anderes Skript, oder
            ci_deploy.sh und rwdeploy.sh passen nicht zusammen.
  Loesung : 3.3 / 3.4; beide Dateien aus demselben Stand nehmen.

  Problem : Job rot: "ERROR: path not allowed: Reports/source/..." oder
            "path not allowed: source/..."
  Ursache : alte rwdeploy.sh (Aufbau Reports/...) auf dem Server, oder
            alte ci_deploy.sh im Repository.
  Loesung : 1.1 (Version pruefen) und SCHRITT 6 (ci_deploy.sh ersetzen).

  Problem : deploy_prod rot: "the tagged commit holds no report (.rdf) or
            image - nothing to deploy, check the tag"
  Ursache : Tag auf einem Check-in ohne Bericht (z.B. nur Skripte).
  Loesung : Tag loeschen (ROLLBACK), mit release_tag.ps1 den Check-in des
            Berichts taggen.

  Problem : deploy_prod rot: "the tag is on a merge commit"
  Ursache : Zwei Kollegen haben gleichzeitig eingecheckt, der Tag sitzt auf
            dem Zusammenfuehrungs-Check-in.
  Loesung : Tag loeschen, mit release_tag.ps1 den Check-in des Berichts
            taggen.

  Problem : Job endet mit "deploy still pending after 300s"
  Ursache : Kopierer laeuft nicht oder ist beschaeftigt.
  Loesung : auf dem Server  $RWD_BIN/rwdeploy.sh list  und
            ls $RWD_HOME/incoming ; dann  $RWD_BIN/rwdeploy.sh work  von
            Hand starten; cron (1.6) pruefen.

  Problem : DEV meldet "WARNING: last deploy ... is not an ancestor"
  Ursache : Die Historie von main wurde umgeschrieben (force push).
  Loesung : Nur die Dateien dieses Check-ins wurden verteilt. DEV pruefen,
            ggf. Startpunkt neu setzen (1.7). Force push auf main
            verbieten (5.1).

  Problem : Im Menue steht ein Eintrag rot "(Skript fehlt)".
  Ursache : Das Skript liegt nicht im Ordner deploy\ des Clones.
  Loesung : git pull (pull.ps1); SkriptPfad in menu.ini pruefen.
